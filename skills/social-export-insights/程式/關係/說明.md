# 關係模組 —— 重要聯絡人關係分析（旗艦範例模組）

示範 7 層架構（見 `分析\架構.md`）L1-L6 全套，尤其是成熟的 L5（可編輯範本＋分派 subagent＋結構化 schema＋可重跑）。這是原專案 `relationships/` 領域的完整移植，把 `ai_<friend>/`（單一好友深度分析原型）泛化成的可重複套用 pipeline：從全部 1:1 對話依重要性排出前 30 名，逐一跑量化分析，並依重要性分兩層做質性關係筆記，彙整成一個 dashboard，筆記同時輸出成 Markdown 供放進個人知識庫。

## 目的與範圍

- 只排 1:1 對話（排除群組、排除疑似垃圾對話），因為「人脈網」本質是「我和某個人」的關係，群組會混雜多人發言、關係歸屬模糊——群組場景見 `程式\群組\` 模組。
- 複製到新專案時，檔名沿用原專案慣例（`build_thread_ranking.py` 等），本資料夾內用 `_template.py` 後綴標示。

## 重要性評分公式

僅用 `messages/data/thread_index.json` 既有欄位（不重掃 HTML），篩選條件：

```
not is_group and not likely_spam and message_count >= MIN_MESSAGE_COUNT_FLOOR
```

指標與意義：

| 指標 | 說明 |
|---|---|
| `message_count` | 總訊息量：關係深度的主要訊號 |
| `span_days` | 首末訊息相隔天數：關係跨度/長期性 |
| `recency_days` | 距離**語料庫最新訊息**（非「今天」）的天數：越近分數越高 |
| `density` | `message_count / span_days`：每日互動密度，區分「長但稀疏」vs「密集」 |
| `media_richness` | 媒體訊息佔比：親密度輔助訊號 |

`recency_days` 刻意用語料庫內所有合格對話的最新 `last_dt` 當基準，而非執行當下的「今天」——見 `分析\踩坑.md` 第 1 條：如果匯出本身在某個時間點被截斷，用「今天」當基準會讓每個人都被同等程度地扣分，沒有鑑別力。

各指標在合格對話池內做百分位排名（0~1，並列取平均排名），加權求和 ×100：

```
importance_score = 100 * (
    0.35 * pct(message_count) +
    0.20 * pct(span_days) +
    0.20 * pct(recency, 越近越高) +
    0.15 * pct(density) +
    0.10 * pct(media_richness)
)
```

權重與門檻都在 `config_template.py` 的 `WEIGHTS` / `MIN_MESSAGE_COUNT_FLOOR` / `MIN_SPAN_DAYS_FOR_DENSITY`，要調整排名邏輯只需要改常數、重跑排名腳本（純 JSON，很便宜，秒級完成）。

## 分層規則

依 `importance_score` 排序，決定**批次全量跑法**下 L4 量化特徵的粒度預設值（成本考量，見下表）；`config_template.py` 的 `TOP_N_DEEP`/`TOP_N_TOTAL` 只控制這個 L4 粒度分界，不再直接決定要不要做質性判讀或做到哪一層——質性判讀现在是輕/中/深三層（見 `分析\分層.md`），依使用者需求指定，不是排名自動決定：

| 排名 | L4 量化特徵粒度 |
|---|---|
| 1~`TOP_N_DEEP`（預設 10） | 月粒度特徵矩陣、SnowNLP情緒、迴歸趨勢、轉折點偵測、KMeans+PCA關係階段分群、逐季jieba主題詞 |
| `TOP_N_DEEP+1`~`TOP_N_TOTAL`（預設 11~30） | 年粒度特徵矩陣、逐年jieba主題詞 |

質性判讀（第 5 步）依使用者對這個目標指定的分析層級選對應範本：輕層通常跳過
（用上面的量化特徵＋幾句摘要就夠）；中層一律用 `範本\中量判讀.md`（事件時間軸
／精選語錄／語氣序列，不分排名高低，只要有既有 `note.md` 可以加值就能做）；深
層在中層之上再疊加逐季質性閱讀（`範本\深季判讀.md`）與完整的月粒度量化建模。
單次全歷程質性通讀（`範本\輕量判讀.md`）現在定位成「還沒有 `note.md` 時，中/
深層判讀的敘事基礎素材來源之一」，不是獨立的一個分析層級。批次架構下仍可用排
名決定「哪些目標值得投資到深層」；隨選問答單一對象時可以一律用深層粒度，見
`分析\問答.md`。

## Pipeline 執行順序（批次全量跑法）

```
0. (若資料已過期才需重跑) social-export-analysis 的 messages/social 相關抽取
1. build_thread_ranking_template.py   -> data/thread_ranking.jsonl, data/top30.json
2. build_person_corpus_template.py    -> quant/<slug>/messages_full.jsonl        (x30)
3. build_features_template.py         -> quant/<slug>/feature_matrix.csv 等      (x30)
4. build_reading_excerpts_template.py -> notes/<slug>/excerpts/*.md              (x30)
5. [Claude 撰寫，非腳本，見下方]        -> notes/<slug>/note.md                    (x30)
5b. (中層以上限定，使用者明確要求時才做) 範本\中量判讀.md -> timeline.json/quotes.json/sentiment.json，跑完務必過 程式\共用\verify_quotes_template.py
6. (深層限定) 每人的 quant report、彙整 dashboard —— 依專案既有 html_report.py 慣例組頁
```

第 6 步假設目標專案（跑過 `social-export-analysis`）已經有共用的 `analysis/lib/html_report.py` 元件庫——這不是本 skill 提供的檔案，是那個 skill／原專案既有的慣例。專案還沒有這個共用模組時，先用純陽春的 HTML（`<table>`/`<ul>`）頂著即可，不要為了單一模組自己刻一套 CSS，等真的要做第二個模組的報告頁時再考慮要不要補一份共用元件庫。

隨選問答模式下，通常只需要步驟 1（聚合問題）或 2-5 針對單一對象（見 `分析\問答.md` 決策表），不必每次都跑完整批次。

## 質性分析（第 5 步，agent 執行而非腳本）

第 4 步的摘錄檔只是取樣素材，真正判讀關係、寫成筆記的工作無法腳本化——這是這條分析線最早的 pitfall：「訊息要盡量逐行閱讀並懂情境，才能釐清關係」，本質上需要語言理解，不是統計腳本能做的事（對應 `分析\架構.md` 的 L5）。

- `範本\深季判讀.md`：深層用，逐季判讀範本，產出 `note.md`。
- `範本\輕量判讀.md`：`note.md` 還不存在時的敘事素材來源，單次全歷程判讀範本。
- `範本\中量判讀.md`：**中層以上都要做**，在既有 `note.md` 之上加值事件時間軸／精選語錄／語氣序列三份 JSON，是「輕/中/深」三層架構（`分析\分層.md`）裡的核心產出，不分排名高低。
- `範本\人物側寫.md`：二次彙整既有筆記，補一段「這個人整體是什麼樣的人」（不重讀原始訊息）。
- `範本\筆記格式.md`：`note.md` 的 YAML frontmatter 規範，dashboard 靠這個規範解析筆記摘要。

執行方式：對每個目標分派一個獨立 subagent，讀該目標 `excerpts/` 底下的摘錄檔＋對應範本，寫出 `notes/<slug>/note.md`。多個目標彼此獨立、無共用狀態，適合平行跑；批次全量跑時建議先做深層（單獨看，內容較多、價值也較高，值得跑完後抽查幾篇），再做輕層（單篇短，可批次一起跑）。

**這是本模組裡唯一可以「學習並優化」的環節**——如果之後發現某篇筆記判讀偏差、或想要不同的關注角度，直接修改對應的範本檔案（不用動任何 Python 程式碼），下次重寫筆記時就會套用新版範本。

## 已知限制

見 `分析\踩坑.md`「跨模組通用坑」「關係模組專屬」與「中層分析新增坑」三節（recency 基準、排除清單、姓名比對、SnowNLP 準確度、關鍵詞誤判、迴歸誤判、輕層取樣取捨、交易性對話混入、社交圈訊號侷限、語錄逐字驗證、agent 自陳涵蓋率不可信）。
