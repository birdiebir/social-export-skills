# 風險模組 —— PR 風險審閱（示範把「手動判讀」升級成「範本化判讀」）

跟 `程式\關係\` 一樣做候選篩選＋質性判讀，但起點不同：原專案 `pr_risk/` 的候選篩選（關鍵字/正則預篩＋分層抽樣）本來就已經是腳本化的，**真正缺的是 L5**——舊版的最終判讀是某次對話裡手動寫出來的散文（`report.md`），沒有範本、不可重現，只是後續被腳本轉成 HTML。本模組把這個落差補上：新增 `範本\審閱判讀.md`，讓「這則內容到底有沒有問題、多嚴重」的判讀變成範本驅動、可重跑，而不是一次性手寫。**這是新設計的範本，不是原專案原封不動搬過來的**——原專案目前沒有這一層。

## Pipeline

```
1. flag_candidates_template.py
   -> data/flagged_candidates.jsonl（關鍵字/正則命中的候選）
   -> data/unflagged_sample.jsonl（未命中內容的分層隨機抽樣，抓關鍵字漏掉的部分）
2. [Claude 執行，非純腳本，見下方「質性審閱」] 讀 範本\審閱判讀.md
   -> data/reviewed.jsonl（每一則候選的真正判讀結果，見 範本\筆記格式.md）
3. finalize_pr_risk_report_template.py
   -> data/final_report.md（依「LLM 判讀的嚴重度」分組排序，reviewed.jsonl 不存在
      時優雅降級成依關鍵字命中類別分組，並在報告中註明這是降級模式）
```

## 為什麼需要 L5，不能只停在關鍵字預篩

見 `分析\踩坑.md` 第 14-15 條：關鍵字/正則預篩一定會漏（反諷、暗語）、也會有假陽性（命中不等於真的有問題）；固定優先順序的嚴重度分組只是「怎麼呈現」，不是真正評估每一項的實際風險程度。真正的判斷——這句話放在什麼上下文裡、是不是玩笑、是不是已經是好幾年前的事、公開程度多高——需要實際閱讀理解，這正是 `分析\架構.md` L5 講的「無法腳本化的一層」。

## 質性審閱（第 2 步，agent 執行而非腳本）

`data/flagged_candidates.jsonl`＋`data/unflagged_sample.jsonl` 只是候選清單，真正判讀由 Claude 讀這些候選＋`範本\審閱判讀.md` 完成，寫出 `data/reviewed.jsonl`（見 `範本\筆記格式.md` 的欄位規範）。

執行方式：候選項目數量通常有數百則，不要一次全部塞進同一個 context——分批處理（每批建議 20-30 則），批次之間彼此獨立、可平行分派給多個 subagent。跟關係模組一樣，**這是本模組裡唯一可以「學習並優化」的環節**——如果之後發現判讀角度需要調整（例如某類內容一開始判太嚴格/太寬鬆），直接改 `範本\審閱判讀.md`，不用動任何 Python 程式碼，下次重新審閱時就會套用新版範本。

## 已知限制

見 `分析\踩坑.md`「跨模組通用坑」與「風險模組專屬」兩節。額外注意：這個模組處理的是使用者自己過去的真實發言/貼文，判讀時務必中立陳述風險而不做道德評價，且**不要自動執行任何刪除/設為私人的動作**——Claude Code 沒有瀏覽器自動化或 FB API 存取權限，最終報告只能是給使用者自己逐項決定的清單，不是自動化清理工具。
