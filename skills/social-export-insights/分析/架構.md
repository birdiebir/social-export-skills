# 7 層通用模式

盤點自 `<export_root>\extracted\analysis\` 至少 8 個已實作領域（`relationships/`、`group_analysis/`、`ai_<friend>/`（單一好友原型）、`pr_risk/`、`security/`、`photo_library/`、`messages/`、`reports/`）後歸納出的通用架構。每個領域都是同一套模式的具體實作，差異只在「套用在誰身上」。新增模組時，先判斷自己落在哪幾層，再照對應層的慣例寫，不要每個模組重新發明一套規矩。

## L1 抽取（Extract）

原始 HTML/JSON → `output/<domain>/data/*.jsonl`，用共用解析函式庫（例如 `fb_common.py`）處理，高量類別用 streaming（絕不整批讀進記憶體），絕對路徑一律從 `paths.py` 算出、不寫死。

**這層屬於 `social-export-analysis` skill，本 skill 的模組一律消費它的產出，不重做。**

## L2 候選排名/篩選

用便宜的已抽取欄位（不重掃原始檔）對一大池候選評分/篩選，縮小成人工可審視的 top-N。

慣例：
- 權重、門檻、排除清單集中在該模組的 `config.py`，改參數不必動 pipeline 程式碼，重跑通常是純 JSON 運算、很便宜（秒級）。
- heuristic 一定抓不乾淨——例行需要一份人工維護的排除清單補漏網之魚（`relationships/` 的 `EXCLUDE_NAMES`：混進客服帳號/本人帳號別名；`group_analysis/` 的 `EXCLUDE_GROUP_NAMES`：廣播群組）。第一次真跑幾乎必然要調整這份清單，不是一次寫對規則就結束。
- **候選池規模大到一定程度後，該有一個可重複執行的涵蓋率儀表板**（2026-09-18 新增，見 `分析\分層.md`「涵蓋率追蹤」與 `程式\共用\coverage_dashboard_template.py`）——追蹤「候選池多大、做了多少、訊息量加權涵蓋率多少、輕/中/深分層分布」，不要每次要回答進度問題就重新手動數資料夾；**候選數量佔比會嚴重低估真實覆蓋度，一定要同時算訊息量加權版本**才能看出「其實最活躍的都已經涵蓋了」這種更有意義的事實。
- **每個模組都該有疊代優化紀錄表**（日期｜變更｜原因），不是只有旗艦模組才配。**這份文件跟生成腳本一樣容易遺失**——實際稽核發現至少一個真實專案的 `relationships/`（原本被認為是最早示範這個習慣的模組）疊代紀錄表已經不存在於磁碟上，成因見 `分析\踩坑.md` 第 24／29 點：方法論文件如果沒有跟著 `analysis/output/<module>/` 一起進 git，只存在產生它的那次 session 裡，下一個接手的人就無從得知它曾經存在過。**判斷某模組有沒有疊代紀錄表，永遠用 `find`/`ls` 實際確認，不要相信 skill 文件或其他模組宣稱「應該有」。**
- 時間基準陷阱：任何「多久沒聯絡/多新」類指標，基準要用語料庫自己最新的時間戳，不能用執行當下的「今天」——如果匯出本身在某個時間點被截斷（例如 Messenger 轉端對端加密），用「今天」當基準會讓所有候選被同等程度扣分、失去鑑別力（見 `relationships/config.py` 的 `recency_days` 計算方式）。

## L3 跨領域 join

合併多個 domain 的 JSONL 產出成新洞察（漏斗、人格推論、主題分類）。

姓名/實體比對的標準做法（`analysis/lib/name_match.py`）：只有在名稱字串於兩份清單裡都恰好出現一次時，才算 `confident_match`；否則進 `ambiguous` 桶，**絕不悄悄合併**，並把這個限制寫進輸出自己的 `_meta.caveats` 欄位（不要只寫在程式碼註解裡，下游消費者不會回頭看程式碼）。同一份邏輯要跨腳本共用，不要每個 join 各自重寫一次比對規則。

## L4 量化特徵/統計

逐目標算統計特徵：關鍵詞頻率（jieba）、情緒分數（SnowNLP，僅供相對趨勢參考——訓練語料是簡體中文商品評論，繁中/英文混雜口語準確度有限）、時間趨勢迴歸、規則式自動標籤。

**規則式自動標籤 pattern**（來自 `group_analysis/config.py` 的 `MEMBER_TAG_RULES`）：對每個指標，取「達最低樣本門檻」的群體裡排名前 X% 的成員，貼一個固定標籤。完全不需要 LLM，適合成本敏感、目標數量多的場景（例如要對 10 組群組的每個成員都下判斷）。**不是每個模組都需要 L5**——先問自己：這個判斷純粹是「誰的某個統計數字比較高」，還是需要真正理解上下文？前者用這個 pattern 就夠。

## L5 LLM 範本化質性判讀

**這是唯一真正無法腳本化的一層**——需要實際理解訊息內容的上下文，不是統計腳本能做的事。這是本架構最重要、也最容易做錯的一層，兩種做法的落差：

- **成熟做法**（`relationships/` 範例）：可編輯的 markdown 範本（`templates/*.md`）定義判讀角度與輸出格式 → 對每個目標分派一個獨立 subagent，讀該目標的摘錄檔＋範本 → 寫出符合固定 frontmatter schema 的結構化筆記 → 可重跑（改範本，下次重寫就套用新版，不用動任何程式碼）。
- **反面教材**（原專案 `pr_risk/` 的舊版 `report.md`）：某次對話裡手動寫出來的散文判讀結果，沒有範本、不可重現，後續只是被腳本轉成 HTML——**這不是範本化，是被腳本包裝過的一次性人工產出**。真的要改判讀角度，得回去重新手寫一次，沒有「改範本就好」這個選項。

新模組如果需要 L5，一律照成熟做法做：範本＋分派＋結構化 schema＋可重跑，不要圖快先手寫一版「之後再範本化」——那個「之後」通常不會發生（`pr_risk/` 就是活生生的例子）。

反過來，如果評估後發現這個判斷用 L4 的規則式標籤就夠（例如目標數量多、單一目標的判斷價值低），就照 `group_analysis/` 的做法明講「刻意不做 L5，原因是 XXX」，不要含糊帶過或漏做。

L5 做到多深不是「做或不做」的二選一，見 `分析\分層.md` 的輕/中/深三層——中層以上的 L5 產出（宣稱通讀過原始訊息、萃取出真實事件與語錄）務必搭配 L7 的機械化驗證，不能只靠 agent 自陳。

## L6 報告/dashboard 組頁

只讀已經算好的 JSON（不重新解析原始檔），用共用元件庫組頁（例如 `html_report.py` 的 `page()`/`card()`/`chart_box()`），圖表用本機 vendor 檔（不依賴 CDN，離線 `file://` 也能開），對尚未完成的個別目標優雅降級（顯示「尚未撰寫」而非報錯——批次處理很多目標時，不會所有目標同時完成）。最後彙整進單一入口頁面。

**`reports` 彙整層現在有真實範例可參照**（2026-09-21 新增，某個真實專案的 `<export_root>\<account_A>\<export_folder_YYYYMMDD>\analysis\output\reports\`）：把 `relationships`／`group_analysis`／`friends_insight`／`personal_activity`／`coverage` 五個既有模組的產出整合成 3 份跨模組總覽頁（社交網絡地圖、跨時間人生時間軸、精選語錄集錦）＋ 1 份模組入口頁，生成腳本在 `analysis\scripts\reports\`（`config.py` 存跨模組分類字典、`common.py` 是共用資料載入層、四支 `build_*.py` 各自產生一份 HTML，皆可獨立重跑）。示範重點：
- **`reports` 層的「分類/歸類」可以是報告本身新增的瀏覽用標籤**（例如把 relationships 的數十人依既有質性摘要人工歸類成「家人／師長／死黨核心圈／同學／遊戲搭檔／協作夥伴／網路陌生人」），不必是來源模組的既有欄位——只要在方法論文件裡講清楚這是彙整層自己加的分類、依據什麼判斷，不影響、不改寫來源模組結論即可。
- **逐月/逐年時間序列可以合法跨模組疊圖**：relationships 的 `feature_matrix.csv`（逐月 `total_messages`）、group_analysis 的 `activity.json`（`monthly_trend`）都是已經算好的 L4 產出，reports 層讀取後依年份加總、疊成同一張跨模組趨勢圖，完全不算「重新解析原始檔」，是 L6 該做的整合工作。
- **旗艦跨時間報告的敘事骨幹，找兩個信號的交叉點最省力**：本例把「個人動態模組的逐年質性敘事」（真人寫的因果解讀）疊在「關係+群組模組的逐年量化訊息量」（結構化數字）上，兩者交叉處往往就是全報告最值得講的故事（本例是帳號轉移事件——活動量斷崖式歸零的年份，剛好對應原始資料中的佐證段落）。
- 完整方法論、資料來源對照表、已知限制見該專案自己的 `analysis/output/reports/README.md`，新專案要做 `reports` 模組時可直接參照複製調整（比照 `分析\擴充.md` 的步驟）。

**模組自己的入口頁（例如 `group_analysis/report.html`），如果底下有多個同類目標（多個群組/多位聯絡人），至少要有一個跨目標比較圖表**（例如依訊息量/事件數排名的長條圖），不能只是一份平鋪的清單——實際稽核發現 `group_analysis/report.html` 列出 10 個群組的卡片，但入口頁本身 0 個 `<canvas>`，看不出「這 10 個群組彼此量體差多少」，使用者得逐一點進去才知道；`relationships/` 跟這次新做的 `group_posts/` 都有做到入口層級的比較圖，可以直接照抄那個 pattern。

## L7 跨領域紀律（貫穿全部層，不是流程步驟）

- **正確性檢查**：新增/修改解析邏輯前後，跑 sanity check（挑代表檔案人工看輸出是否合理）與 regression check（重新解析已處理過的來源檔，比對筆數是否一致）。
- **自我驗證的 docstring**：每支腳本記錄自己第一次成功跑出的預期筆數，下次重跑時可以一眼看出有沒有跑壞。
- **config 集中**：任何會調的常數（權重、門檻、關鍵詞表、排除清單）集中在模組自己的 `config.py`，不要散落在 pipeline 程式碼裡。
- **先查共用 lib，而且要把生成腳本本身留下來讓「先查」這件事有意義**：寫新邏輯前先確認 `analysis/lib/` 有沒有現成的（姓名比對、hardlink、路徑、HTML 解析），不要每個模組各自重寫一份。這件事本身就是一個曾經被抓出來、後來修正的真實案例——見 `分析\踩坑.md` 裡 UI 不一致的那條。**但這個紀律有一個前提：生成腳本本身要真的留在磁碟上（並進 git）**。實際稽核發現至少一個真實專案完全沒有 `analysis/lib/`，連既有模組（`relationships`/`group_analysis`/`pr_risk`/`ai_<friend>`）自己的生成腳本都不存在——只有最終 HTML/JSON 輸出被提交，Python pipeline 從沒進過 git。結果新模組只能靠讀既有 HTML 反推慣例，做不到真正 import 共用程式碼。新增或擴充任何模組時，順手把這次寫的生成腳本、`config.py`、`README.md` 也提交進 git（不是只提交 `analysis/output/` 的最終產出），下一次「先查共用 lib」才有東西可查。見 `分析\踩坑.md` 第 24 點。
- **新模組動手前，先查有沒有別的模組已經處理過同一份原始來源**：如果新模組的資料來源（例如某個 `.html` 匯出檔）已經被另一個既有模組抽取/分析過，動手前先看一眼那個模組的產出，交付新發現時如果跟既有模組結論重疊或矛盾，要在兩邊的 `_meta.caveats`／README 互相註記，不要各自獨立收斂到同樣的結論卻彼此不知道對方存在。見 `分析\踩坑.md` 第 28 點（`pr_risk` 與 `group_posts` 各自發現同一批政治論戰內容卻互不知情的案例）。
- **中層以上的 L5 產出要機械化驗證，不能只信任 agent 自陳**：語錄逐字性與涵蓋率完整性都用得到，共用腳本見 `程式\共用\verify_quotes_template.py`／`verify_coverage_template.py`，用法與門檻見 `分析\分層.md`。這是本架構文件寫成後才補上的一層紀律，起因是實跑中發現 LLM 產出「幾乎逐字」的語錄（意譯、截斷、拼接兩則訊息）是最常見、也最容易被人工抽查漏掉的品質問題。
- **多個 agent 平行擴充同一個模組時，不要讓大家都去編輯共用文件**（總覽頁 `index.html`／模組入口 `report.html`／`README.md` 的疊代紀錄表）——就算每個 agent 都很小心用純追加方式編輯，同時寫同一份文字檔還是有真實的競態風險。做法：每個 agent 只准新增全新檔案／編輯自己專屬的子資料夾，共用文件的更新內容改成在最終報告裡附上建議文字，由 controller 收到全部 agent 的報告後親手一次合併（合併時要重新核算正確的總數，不能把兩份各自以為自己是「第一個/第二個」的敘述原封不動疊在一起）。多個 agent 平行擴充**同一支參數化共用腳本**（例如同一支深層分析產生腳本要支援多個目標）則相對安全，只要收斂到「新增一個 profile 鍵值」的加法架構、遇到並發寫入錯誤時重新讀取再用局部 Edit 合併、收工前重新驗證既有呼叫方式輸出不變，見 `分析\踩坑.md` 第 35-36 點。

## 演進案例：`ai_<friend>/` → `relationships/`

原專案自己示範過一次「把 ad hoc 做法產品化」，值得當成新增模組時的參照：`ai_<friend>/`（單一好友的手工原型，資料夾以那位好友命名，最早驗證出 L4/L5 的分析方法）泛化成 `relationships/`（30 人通用版）時，具體做了這些事——bespoke regex parser 換成共用的 `fb_common.iter_messages()`（L1 紀律）；硬編碼的姓名常數換成通用的 `role` 欄位（讓同一份程式碼套用在任何目標身上）；不一致的獨立 CSS 換成共用元件庫（L6 紀律，修正原型模組舊報告沒套用元件庫的問題）；1 人擴到 30 人靠新增的深/輕分層控制成本（L2/L4 的分層規則，是「候選數量增加後怎麼繼續用得起 L5」的具體解法）。這正是本 skill 要做的事再往上一層：把「產品化」這個動作本身變成可重複套用的架構，而不是每次都重新摸索一遍。
