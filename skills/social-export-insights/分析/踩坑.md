## 跨模組通用坑

1. **時間基準要用語料庫自己的最新時間，不能用「今天」**——如果匯出本身在某個時間點被截斷（例如 Messenger 轉端對端加密後，「下載你的資訊」就抓不到之後的內容），所有對話的匯出都在同一時間點被截斷，跟關係/群組本身是否還活躍無關；用執行當下的「今天」當基準會讓每個候選被同等程度扣分，失去鑑別力。任何 `recency`/`最近`類指標都要檢查這件事。
2. **候選排名第一次真跑一定會混進非目標對象**——`thread_index.json` 沒有「是否企業/自己帳號」欄位，無法用 heuristic 完全排除。第一次真跑後照樣要人工看過候選清單、把明顯不是目標的項目加進排除清單（`EXCLUDE_NAMES`／`EXCLUDE_GROUP_NAMES` 這類），這是預期中的疊代步驟，不是規則沒寫好。
3. **姓名/實體比對只信「唯一匹配」**——一個名稱字串在多年匯出裡不是穩定的 key（改名、同名不同人）。只有在兩份清單裡都恰好出現一次時才算 confident，否則進 ambiguous、絕不悄悄合併，並把限制寫進輸出的 `_meta.caveats`。
4. **SnowNLP 情緒分數只能當相對趨勢參考**——訓練語料是簡體中文商品評論，用在繁中/英文混雜的日常口語對話上準確度有限，永遠要跟質性判讀交叉驗證，不要單獨信任。
4a. **`message_N.html` 的頁碼順序不等於時間順序**——Facebook 匯出的分頁慣例是新到舊排列，逐檔讀取後一定要依 `dt` 重新排序（`msgs.sort(key=lambda m: m["dt"])`），不能假設檔案本身的頁碼順序就是聊天時序。這是原專案 `build_message_archive.py` 已經踩過、修過的坑，語料抽取類腳本（`build_person_corpus_template.py`／`build_group_corpus_template.py`）都直接複用了正確做法，但新寫任何會讀 `message_N.html` 的腳本時，還是要自己確認有沒有補這一步。
5. **關鍵詞頻率統計會漏掉反諷/玩笑**——簡單字串比對抓不到語境，質性判讀（如果有做 L5）能修正，但量化圖表本身不會自動修正，呈現時要註明這個限制。
6. **迴歸/轉折點偵測在低樣本期容易誤判**——早期月份/資料量少的區段自然容易偏離全期趨勢線，不代表真實的轉折，解讀時要留意樣本數。
7. **取樣上限是刻意的成本/顆粒度取捨，不是 bug**——例如輕層摘錄的訊息則數上限、代表天數上限，是為了讓大量候選（例如 20-30 個）都能被質性判讀覆蓋而做的犧牲，判讀出來的內容較淺是預期結果，不用想著「修正」。
8. **共用邏輯不要各模組各自重寫**——原專案曾經出現不一致（單一好友原型模組 `ai_<friend>/` 的報告用了獨立 CSS＋CDN Chart.js，沒套用後來才建立的共用元件庫），後來才被回頭修正。寫新邏輯前先查 `analysis/lib/` 有沒有現成的。
9. **L5 判讀沒範本化，之後很難補救**——一次性手寫的質性判讀（原專案 `pr_risk/` 舊版 `report.md`）沒有範本、不可重現，要改判讀角度得整份重寫。需要 L5 就一開始範本化，不要想著「先手寫一版之後再補範本」。

## 關係模組專屬

10. **交易性對話會混進候選榜**（觀察到但未修）：短租房客、代購糾紛、Marketplace 二手買賣這類對話往往短時間內密集往返、常附照片，重要性分數會虛高，但質性內容其實很淺，不是真正的人際關係。目前只能靠質性判讀誠實標註（如「非個人朋友關係」），量化排名本身不會自動排除。未來可考慮加交易偵測訊號（金額/議價關鍵詞密度、訊息高度集中在少數幾天）當扣分項。
11. **社交圈訊號目前只有家人關鍵詞比對**，沒有像最早的單一好友原型那樣對全部好友名單逐一做具名提及比對——對候選數量多的場景成本高、邊際價值低，是刻意的取捨，不是漏做。

## 群組模組專屬

12. **廣播型大群組要排除，不只是排除垃圾群組**：參與人數過多的課程/廣播型群組，多數成員從未發言，「每個成員的分析」對他們沒有意義，跟「疑似垃圾對話」是兩種不同的排除原因，要分開判斷。
13. **通用垃圾偵測會有假陰性**：廣義的關鍵字/規則判斷會漏掉部分內容（例如特定語言的敏感內容關鍵字沒涵蓋），需要模組自己額外維護一份排除清單，不影響通用判斷本身。

## 中層分析新增坑（2026-09-16，`分析\分層.md` 三層架構落地時踩過）

以下是導入「輕/中/深」三層架構、把數十位聯絡人與約 10 個群組全部做到中層時，第一次真跑才發現的坑，跨模組通用。

16. **LLM 自稱「語錄已核對逐字」不可信，一定要跑機械化驗證**——最常見的失敗模式是意譯（改寫但語意相近）、截斷（原文很長，用「……」收尾但沒複製完整）、拼接（把時間相近的兩則獨立訊息合併成一則「語錄」）。這三種都會通過人工快速掃過的肉眼檢查，但逐字字串比對會抓到。務必用 `verify_quotes_template.py` 對每一筆 `quote`/`evidence_quote` 做子字串比對，不通過就是沒做完，回頭修那一筆，不是重跑整份。
17. **agent 自我回報的「涵蓋率」不能當完成標準**——曾發生 agent 主動誠實回報「這次只涵蓋了 20% 左右」卻仍把結果當成可接受的最終產出提交；也發生過 agent 把「不要重讀已經讀過的部分，接著讀」誤解成「可以提早結束」。涵蓋率要用 `verify_coverage_template.py` 核對 `coverage.json` 的 `messages_read` 是否等於來源檔的實際行數，不能只信任 agent 自己說的百分比。
18. **大量訊息群組要拆批＋合併，不能塞給單一 agent 一次讀完**——數萬則訊息的群組全量通讀，切成 4 個獨立子區間分派給不同 agent，各自輸出中繼檔（`chunk_*.json`），再由合併步驟跨全期去蕪存菁（不是每個子區間各自硬湊事件/語錄數量）並保留敘事弧線，合併通過驗證後才刪除中繼檔。子區間切法：依日期切，每段落在幾萬則以內，訊息量特別大的月份不要跨區間切開。
19. **輕/淺資料目標要優雅降級，不要為了版面一致硬湊**——部分目標沒有逐季分段的敘事（只有一整篇）、或沒有既有的量化報告頁，中層合併頁遇到這種情況要省略對應區塊或用簡化版頂替（例如用 `meta.json` 現有欄位做一個陽春統計區塊），不要為了跟深層目標的版面長得一樣而虛構資料或段落結構。
20. **資料夾名稱裡的破損 emoji（真的變成 U+FFFD 位元組，不是顯示問題）**——原始匯出檔名裡的表情符號在某些情況下會變成無法還原的替代字元，`Glob` 抓不到這種路徑，要改用 Bash 的 `find -iname "關鍵字*"` 找出真實路徑，並在 Read/Write/Edit 工具的路徑參數裡原樣貼上那個替代字元（不要嘗試「修正」檔名，那是既有匯出檔的一部分）。
21. **Windows 主控台的 legacy 編碼（如 cp950）會讓驗證腳本本身在印結果時就當掉**——跟驗證邏輯本身無關，是 `print()` 遇到主控台編碼不支援的字元（例如某些聯絡人/群組名稱裡的字）直接拋 `UnicodeEncodeError`，讓人誤以為驗證失敗。腳本要在開頭強制 `sys.stdout` 用 UTF-8（見 `程式\共用\verify_quotes_template.py` 開頭的寫法）。
22. **核對渲染後 HTML 裡某個 class 出現次數時，`grep -c` 算的是「符合的行數」不是「出現次數」**——自動產生的報告頁常常整份檔案就是一行（沒有換行），這時候 `grep -c` 永遠回傳 0 或 1，不管實際出現幾次，要改用 `grep -o 樣式 | wc -l`。另外，CSS 選擇器本身也會包含同名字串（例如 `.event-card { ... }` 這條規則本身就會被算進「event-card 出現次數」），核對「內容筆數是否等於來源 JSON 筆數」時要先確認 CSS 規則貢獻了幾次額外出現、扣掉再比對，不然會誤判為筆數不符。
23. **API rate limit 或其他中斷發生後，不要盲目整批重跑**——先稽核磁碟上實際落地的內容再決定：常常任務其實已經完成大半甚至完全做完，只是漏了收尾步驟（例如漏了對應的 CSS 規則、漏了刪除中繼檔、漏了最後一次驗證），補完收尾遠比整個重做便宜。多個 agent 平行編輯同一份共用檔案（例如總覽頁的連結列表）時也可能出現「看到別的 agent 剛好同時完成的結果，誤以為是自己的腳本寫壞了」的假警報，先用 `git diff`/`git log` 核對再下結論，不要急著用 `git checkout` 復原。

## 多模組擴充後的技術/效果/效益體檢（2026-09-17，把架構套用到社團貼文/個人動態/好友資訊三個新模組之後，回頭審查全專案既有模組時發現）

以下是新增 `group_posts`/`personal_activity`/`friends_insight` 三個模組後，對照既有 `relationships`/`group_analysis`/`pr_risk`/`ai_<friend>` 做一次跨模組稽核（重跑驗證腳本、抽讀 note.md、比對排名依據，不是只看 agent 自陳）才發現的問題，跟前面「中層分析新增坑」是同一批性質、但發生在專案已經有多個模組之後才浮現，值得單獨記一節。

24. **生成腳本／README 沒有跟著 commit，下一次擴充等於從零猜慣例**——實際稽核發現這個專案的 `analysis/lib/`（`html_report.py`／`name_match.py`／`fb_common.py`／`paths.py`）完全不存在，`relationships/`／`group_analysis/`／`pr_risk/`／`ai_<friend>/` 這幾個既有模組產生它們的 Python pipeline 腳本也完全沒有留在磁碟上——git 歷史顯示這個專案的 baseline commit 只提交了 `analysis/output/`（最終產出），沒有任何 `.py` 生成腳本（`analysis/pipeline/` 底下當時只有 2 支驗證腳本）。後果是：新增 `group_posts`/`personal_activity`/`friends_insight` 三個模組時，完全沒有既有程式碼可以 import／延伸，只能靠讀既有 HTML 反推 CSS class／JSON schema 慣例（見 `分析\分層.md`「先做一份範例…」那條），比真的有共用 lib 可 import 慢得多、也更容易在細節上跟舊模組不一致。**這個專案本身的教訓，適用於所有專案**：新模組的生成腳本、`config.py`、`README.md` 都應該跟著 `analysis/output/<module>/` 一起進 git（不是只提交最終 HTML/JSON），下一個接手的 agent（不管是不是同一個 session）才有真正的程式碼可以延伸，而不是每次都重新逆向工程一次既有慣例。
25. **`verify_quotes.py`／`verify_quotes_template.py` 原本有一個真的 bug（已修）**：逐字比對前沒有正規化空白字元。Messenger 原始訊息偶爾會把連續幾行短訊息合併成一筆紀錄，中間夾雜真實的 `\n` 換行符；`quotes.json` 為了可讀性把這些換行攤平成空格時，逐字子字串比對就會誤判為「找不到對應原文」（假陰性，不是語錄真的有問題）。已在 `程式\共用\verify_quotes_template.py` 加上 `_normalize_ws()`（把連續空白/換行都收斂成單一空格再比對，兩邊都做），修正後既有 PASS 案例仍然 PASS，真的捏造的語錄依然正確判定 FAIL。**這個 bug 曾經在 `relationships/` 數十位聯絡人身上完全沒被抓到過**——因為多數目標從來沒有人實際手動跑過這支驗證腳本，只是假設「之前已經驗證過」，是本節第 28 點「有驗證腳本不代表真的被拿去跑」的具體案例。如果你複製了舊版 `verify_quotes_template.py`，記得先確認有沒有這個正規化步驟。
26. **深層/資源密集分析的候選門檻不能只看排名複合分數，尤其當分數是用「百分位排名」而非原始數值加權時**——事後用線性回歸把 `relationships/` 的排名公式精確還原出來（R²=1.0）：`35% 訊息量 + 20% 關係跨度 + 20% 近期活躍度 + 15% 互動密度 + 10% 媒體豐富度`，但五個特徵在加權前都先轉成「贏過候選池裡幾 % 對象」的百分位排名，不是直接用原始數值。候選池裡有大量訊息數僅個位數到幾十則的陌生人/交易對話，導致百分位公式對「量級」不敏感：一位只互動十來天、不到一百則訊息的陌生人二手交易對象，靠贏過池子裡大多數低量體候選就能拿到接近深層門檻的高分，擠進深層量化建模，而量化結果自己也誠實承認「找不到顯著趨勢，可能是因為對話跨度較短」；反過來，一段訊息量上萬則級、真實維持好幾年的密切關係，卻因為「近期活躍度」那 20% 權重被停止聯絡多年拖累，總分被壓到原始候選池的前 30 名之外，完全沒被排進中層以上的分析。**百分位排名法的特性是「贏過池子裡多少人」，不是「原始量體多大」**——候選池成分（有沒有大量低量體雜訊候選）會直接決定這個問題的嚴重程度。挑深層候選時，除了排名分數，要多加一道質性初篩：另外看一眼候選的原始 `message_count`/`span_days`（不是百分位），自問「這個對象有沒有值得深挖的敘事理由」，不是分數前 N 名就自動派工，也不要假設分數高的候選量體一定大。
27. **中層事件/語錄擷取數量不能用固定張數，要依內容量體級距調整**——`group_analysis/` 的中層固定每組擷取約 N 則（固定值）`events_narrative` 事件，結果上萬則訊息的群組（大型社群衝突/版規/糾紛內容豐富）和兩三千則訊息的群組（社交閒聊為主）擷取出的事件數幾乎一樣多，等於前者的真實壓縮比是後者的好幾倍，密度高的目標明顯有更多值得記錄卻被漏掉的內容。抓事件/語錄數量時該依來源量體分級距（例如每 N 則訊息 ≈ 1 則候選事件，或至少設一個隨量體增加的上限而非常數），而不是不管量體大小都抓同一個張數。
28. **新模組跟既有模組如果吃同一份原始來源，務必互相檢查有沒有重複發現**——`pr_risk`（規則/關鍵字式 L4，早於這次擴充建置）跟這次新做的 `group_posts`（全量通讀 L5）都是從同一份 `group_posts_and_comments.html` 抽出資料，卻各自獨立收斂到同樣兩個行為模式（政治論戰用詞密集、同一則廣告短時間內廣播貼進大量社團），彼此完全不知道對方的存在，`_meta.caveats` 也沒有互相引用。兩種方法各自獨立收斂到同一結論其實是交叉驗證成功的訊號（值得留著當佐證），但當作「新發現」呈現給使用者之前，應該先查一下有沒有別的模組已經處理過同一份原始來源、結論是否一致——不查就有可能重複告知使用者同一件事，或更糟：兩邊結論不一致卻沒人發現。
29. **模組自己的方法論文件可能在專案裡遺失，不能假設「文件說有就真的有」**——`分析\架構.md` 曾經寫「只有 `relationships/` 有疊代優化紀錄表」，但實際稽核這個專案時，`relationships/` 資料夾底下完全沒有 `README.md` 或任何疊代紀錄檔案，很可能跟第 24 點同一個根因（生成過程的文件沒跟著進 git）。**引用其他模組「應該有什麼」之前，先用 `find`/`ls` 實際確認檔案還在，不要照字面相信 skill 文件或其他模組的既有說法。**
30. **不同時期建立的分層 tier 標記，字面意義可能已經跟現行分層定義脫鉤**——`relationships/` 部分筆記的 frontmatter 寫 `tier: light`，但那是套用「輕/中/深」三層架構前、`relationships/` 自己舊版二層制的殘留值，在舊制底下的「light」其實包含完整 L5 敘事（等於現行定義的「中」），跟現行「輕層＝通常不做 L5」的定義完全不同。如果字面相信這個 tier 標記，會誤判這篇筆記只有量化、沒有質性敘事。**分層定義變動後，既有筆記的 tier 欄位不會自動跟著更新**——判斷一篇筆記實際做到哪一層，要看它實際有哪些檔案（有沒有 `note.md`/`timeline.json`/`quotes.json`），不要只信 frontmatter 裡的字面值。

## 深層量化與多專案並行擴充新增坑（2026-09-18，把群組深層方法論從零建起、對11個既有深層範例做關鍵詞品質稽核、同時擴充兩個姊妹專案時踩過）

39a. **原始匯出檔本身可能把雙方訊息的 sender 欄位錯記成同一個名字，不是解析器 bug，這種候選要排除**：某個 1:1 對話候選（名稱格式異常，像「參與者：X和Y」而非單一姓名，這種命名格式本身就是警訊）全量讀完後，核對原始 HTML 的 `<h2>` 講者標籤，確認 Facebook 匯出檔案本身就把雙方所有訊息的 sender 都記成同一個名字——self/other 完全無法拆分，即使內容本身很有戲劇性（例如爭執/道歉這類值得記錄的情節）也要排除，不能因為內容精彩就勉強做（沒有 self/other 之分，寫出來的 note.md 會誤導讀者以為是單方獨白）。判斷方式：候選名稱本身若是「參與者：A和B」這種格式（而非單一人名），或中層分析途中發現訊息全部歸給同一人卻明顯有兩種語氣風格交替，都要停下來回頭核對原始 HTML 的講者標籤，不要假設解析結果一定正確。

39b. **量體不大的候選裡，常見的排除類型不只是行銷/交易帳號，還有客服機器人與制式回覆機器人**：全量讀完發現的另外兩種排除模式——遊戲官方客服帳號（內容是「玩家向官方客服投訴」的制式往返，非個人關係）、占卜/籤詩類聊天機器人（固定罐頭回覆如「輸入『抽籤』」）。這兩種都會被候選排名公式正常收錄（訊息量/跨度數值上看起來像普通對話），只有質性初篩讀過內容才抓得到，不能只看排名分數或候選名稱判斷。

39c. **候選裡偶爾會出現不對稱的長輩/師生關係，不是同儕朋友——質性判讀要如實標註關係性質，不要預設所有中層候選都是平輩朋友**：候選裡出現過本人的師長、本人的長輩兩種案例，內容（校務往來對話；生活關懷對話）跟朋友社交圈明顯不同調性，若不特別標註，後續使用者或下游分析容易誤把這些人當成同儕朋友圈成員來解讀社交網絡。

39d. **候選對話裡如果出現自傷/輕生意念這類敏感內容，質性判讀要照原文脈絡如實記錄本人當下的回應（勸阻/關懷），不迴避不渲染，也不要延伸臆測沒有根據的內容**——這類內容的處理原則跟其他所有逐字語錄一致（verbatim、不改寫），差別只在於敘事語氣要克制，聚焦在「當下實際發生了什麼、本人怎麼回應」，不要加上超出原始對話內容的心理側寫或後續發展猜測。

39. **`analysis/lib/fb_common.py` 的正則版 `parse_timeline()`，在某些巢狀 `<div>` 結構下會提前收尾，導致時間戳完全抓不到——這是真的函式庫 bug，不是專案特有問題**：在一個仍保有完整 `analysis/lib/` 共用函式庫的專案裡（多數專案這份函式庫已遺失，見第24點），兩個完全獨立、互不知情的 agent（分別建置 `personal_activity` 與 `group_posts` 兩個新模組）各自嘗試沿用 `parse_timeline()` 解析同一批來源（`your_posts...html`／`comments.html`／`group_posts_and_comments.html`），都獨立發現同一個症狀：`<footer>` 裡的時間戳記全部被抓成空字串（例如上千筆留言的 timestamp 全空）。兩人都改成自己在腳本內用 BeautifulSoup／自訂逐 section 解析繞過，沒有回頭修 `fb_common.py` 本體——**這是正確的當下決策**（沒有涵蓋全部既有呼叫端的回歸測試前，貿然改共用函式庫風險大於效益，見 L7 紀律的 sanity/regression check 要求），但代表 `fb_common.py` 本體確實有一個尚未修的真實 bug，兩個獨立案例互相印證、不是巧合或誤用。**下次遇到「原本可靠的共用解析函式突然抓不到資料」時，先懷疑函式庫本身有邊界情況的 bug，不要只當成這次來源特例**；真的要修 `fb_common.py` 本體，要先對現有全部呼叫端（訊息/關係/群組模組）跑一次回歸比對，確認修完後既有解析結果不變，才能安全合併，不要邊做新模組邊順手改共用函式庫。

31. **1:1對話的關鍵詞/主題詞抽取，系統樣板文字會混進真人語料，群組聊天通常不會有這個問題**——`relationships/` 既有深層範例的 `topic_keywords_by_quarter.json` 抽出「位址」「電話給」「將快速心情設定為」這類無意義詞，追根究柢是 Messenger 匯出裡的通話紀錄（「X 打了電話給你。通話時間：25秒」）、未接來電、IP位址登入通知、暱稱/主題變更通知被當成真人訊息逐字納入語料；**最隱蔽的一種是「訊息心情反應通知直接接在真人訊息文字尾巴」**（例：「（真人訊息文字）❤Account B (M月DD日...)」，前半真內容、後半是反應通知），肉眼掃過容易忽略。群組聊天幾乎沒有這類系統樣板（頂多有成員加入/退出事件，通常已被獨立標記為 `is_event` 而非混進訊息文字），所以同一套「jieba+停用詞」抽詞邏輯直接套用在1:1對話語料時，還要**額外疊加系統樣板正則排除＋反應尾綴切除**（切除後保留前半真內容），不能照抄群組模組的抽詞腳本就假設乾淨。動手修之前務必先讀幾季原始 `messages_full.jsonl` 逐字比對，不要假設「加了停用詞就夠」。
32. **盤點「候選池裡誰量體最大、最該做深層」時，要把候選池裡已經完成中層的舊目標也一起比較，不能只比較還沒做的候選**——曾經發生模組 README 稽核時寫「XX是候選池裡唯一夠格深層的候選」，但實際上候選池裡訊息量最大的兩個目標，是更早一批（不同時期、不同任務脈絡）就已經做完中層的目標，稽核時沒把它們拉進同一份排序比較，導致真正該優先做深層的候選被漏掉了兩輪。**核實「下一個深層候選是誰」時，永遠對整個候選池（不分是否已完成中層）依原始量體重新排序一次，不要只看「未分析」清單。**
33. **群組深層量化建模的方法論已經有具體範例可抄，不再是空白**——`分析\分層.md` 過去寫「群組模組深層尚未定義，真的要做時另外設計」，2026-09-18 已經填上具體設計（把 `relationships/` 深層的「兩人 self/other」特徵改寫成群組整體的「發言集中度」`top_sender_share`／`gini_concentration`／相異主動發起人數 `distinct_initiators`，關鍵詞詞庫依群組性質置換，如版務向/揪團向/粗口向），新增群組深層模組時先讀那份更新，不要重新從零設計。
34. **深層量化建模（尤其線性迴歸）不保證拿到統計顯著結果，活動型態是否單調才是關鍵，不是訊息量大就一定顯著**——同一套方法論分別套在三個不同活動型態的群組上：漸進式衰退型（13/22項特徵p<0.05顯著）、長跨度多階段起伏型（約15/23項顯著）、「高原＋斷崖」式驟降型（僅3/22項顯著，因為線性迴歸對非單調形狀天生檢定力不足，且有效月份數少）。**PCA+KMeans生命週期分群在各種活動型態下都比線性迴歸穩健**，即使迴歸大多不顯著，分群仍能抓到迴歸看不到的階段轉折。交付深層分析結果時，統計不顯著要如實呈現並解釋型態原因，不要為了「看起來像有發現」而挑著顯著的講、藏起不顯著的大多數特徵。
35. **多個 agent 平行擴充「同一支參數化共用腳本」（例如同一支深層分析產生腳本要支援多個目標/profile）是可行的，但要有明確的架構收斂點**——安全模式：(1) 第一個完成的 agent 先把腳本從單一目標寫死改成 `PROFILES = {key: {...}}` 這種可插拔字典架構；(2) 後續 agent 一律用「新增一個 profile 鍵值」的加法方式擴充，不整檔覆寫；(3) 遇到「檔案自上次讀取後已變更」的保護性錯誤時，重新讀取後改用局部 `Edit` 精準定位插入點，不要覆蓋對方剛寫入的內容；(4) 每個 agent 收工前，都要重新對「不帶新參數／帶既有profile參數」的呼叫方式跑一次，確認既有輸出逐位元組不變。這套模式讓兩個完全不知道彼此存在的平行 agent，成功在同一支腳本上疊加擴充而互不覆蓋。
36. **平行擴充同一個模組時，不要讓每個 agent 各自編輯共用的 README/總覽頁（`index.html`／模組入口 `report.html`）**——就算個別 agent 都很小心用「純追加」方式編輯，多個 agent 同時寫同一份文字檔還是有真實的競態風險（後寫入者可能覆蓋先寫入者剛存的版本，或編輯器基於過期內容做替換）。做法：每個 agent 只准新增全新檔案／編輯自己專屬的子資料夾，共用文件的更新內容改成「在最終報告裡附上建議加入的文字」，由 controller 收到全部 agent 的報告後，親手一次合併進共用文件（要注意多份報告如果各自誤以為自己是「唯一/第二個」做這件事的人，合併時要重新核算正確的總數，不能把兩份「已完成第2個」的敘述原封不動疊在一起）。
37. **呈現「候選池覆蓋了多少」時，候選數量佔比會嚴重低估真實覆蓋度，要同時算訊息量加權版本**——例如候選池上千個候選只做了幾十個（數量佔比不到 3%），但這幾十個候選涵蓋了全候選池八成以上的訊息量（因為排名方法論本來就優先做重要/活躍的候選）。只呈現數量佔比會讓使用者誤以為進度嚴重落後，而看不出「其實最活躍的都已經涵蓋了」這個更有意義的事實。任何候選池式模組要回報進度時，兩個數字都要算：`已分析數／候選池數` 與 `已分析候選的訊息量加總／候選池全部訊息量加總`，並清楚標註兩者的差異意義。
38. **不同時期產生的候選訊息計數，口徑可能不一致，重跑分析前要先核對**——用全文檢索資料庫（FTS）重建對話語料時得到的訊息筆數，跟原始 L2 候選排名檔案（`thread_ranking.jsonl` 這類）記錄的 `message_count` 可能對不上（FTS索引通常不收錄純貼圖/已讀通知等無文字內容的訊息）。發現落差時不要預設是資料有缺漏，要先確認是不是兩種不同的統計口徑，並在 `coverage.json`／README 裡明確寫出用的是哪個口徑、跟候選排名檔案的原始數字差多少，避免被誤讀成「涵蓋率不足」。

## 最終稽核與跨帳號分析新增坑（2026-09-18，對整個已擴充多輪的專案做最終QA稽核、以及對兩個屬於同一人的姊妹專案做跨帳號綜合分析時踩過）

40. **`verify_coverage_template.py` 原本寫死假設 `coverage.json` 一定有 `batches[]` 陣列，模組間 schema 不同會被誤判為全部 FAIL**——群組類模組（分批全量通讀）的 `coverage.json` 有 `batches[]` 明細很合理，但聯絡人類模組如果是單一 agent 一次讀完（不用拆批），`coverage.json` 用扁平的 `messages_total`/`messages_read` 兩個數字更自然，不该被逼著硬塞一個只有一筆的假 `batches` 陣列。本檔案已修好支援兩種 schema（沒有 `batches` 鍵就跳過該項檢查，只比對總數與已讀數），若你複製了舊版本，記得先確認有沒有這個 schema 分支，不要看到一整批 FAIL 就以為資料真的有問題——先看錯誤訊息是不是 `KeyError` 或格式不符，不是數字真的對不上。
41. **候選對話裡如果分析主體的代名詞判斷錯誤（例如他／她用反），根因常常是被帳號/暱稱的字面性別暗示誤導，不是隨機筆誤**——一個真實案例：帳號本人性別欄位（`identity/data/self_names.jsonl` 這類系統自動生成資料）明明記載為某一性別，但分析全文用了相反的代名詞稱呼本人，推測是被帳號名稱裡某個帶有性別語感的英文暱稱誤導。**寫任何質性分析前，先查一下這個模組有沒有收錄性別/身分欄位（`identity/` 模組），核對一次代名詞用法是否跟資料吻合，不要只憑帳號名稱的語感判斷性別**；已經寫完的分析，建議也抽查一次代名詞一致性，尤其英文/中性/跨語言暱稱的帳號更容易出這種錯。
42. **Marketplace 二手拍賣的重複買家對話，可以用命名格式規則批次排除，不用逐一質性初篩**——候選排名檔裡如果某個「候選姓名」欄位其實是「買家名 · 商品標題」這種格式（例如賣家把商品名稱設成聊天對象顯示名稱的一部分），這種格式本身就是可辨識的訊號，掃過一輪候選池全部抓出來，一次性排除，比每次擴充候選池都要重新靠質性判讀一個個抓有效率得多，而且不容易漏。發現這種可辨識命名格式時，優先寫進 `EXCLUDE_NAMES` 旁的說明註解（「凡符合此格式者一律排除」），而不是每次都重新讀過一遍才想起來。
43. **兩個獨立的資料匯出如果懷疑是同一人的不同帳號，Facebook 系統自動產生的個人檔案欄位（生日、性別等，非本人手動輸入的貼文/聊天內容）是比對話內容更難偽造、更有力的身分證據**——內容層的證據（共同朋友圈、地點、事件時間點）容易被質疑成「兩個相似的人」，但如果兩份獨立匯出檔案裡系統自動記錄的生日欄位完全吻合，這種巧合機率極低，是身分確認鏈裡優先級最高的一項證據，值得在起手比對身分時就先檢查這個欄位，而不是最後才想到。
44. **深層量化分析如果採「混合方法」（例如用關鍵字掃描定位事件、只對命中片段逐一核對原文，而非逐則通讀全部訊息），語錄逐字驗證仍然可以通過（因為每一筆引用的語錄本身確實逐字核對過），但這不等於符合「中/深層＝全量通讀」的硬性定義**——語錄驗證跟涵蓋率驗證是兩件独立的事，前者保證「寫出來的每一句話都真的存在」，後者保證「所有訊息都被讀過、沒有漏看可能更重要的內容」。用混合方法做深層分析時，`coverage.json` 或 `field_notes.md` 要誠實揭露實際採用的方法與真人工通讀的比例，不要讓「語錄驗證全過」造成「涵蓋率也一定達標」的錯覺。稽核者檢查中/深層產出時，這兩項要分開確認，不能因為前者過了就跳過後者。

## 多個獨立 session 並行建置「同一個」新模組新增坑（2026-09-21，兩個互不知情的 Claude Code session 同時被指派為 Account A 專案建置風險模組時踩過）

這一節記錄的是跟第 35-36 點性質不同的並行問題：第 35-36 點是「我（單一 controller）主動分派多個自己的 subagent」，衝突可控、可事先設計收斂規則；這裡是**兩個完全獨立、互不知情的頂層 Claude Code session**（很可能是使用者/上層協調流程重複指派了同一個模組給兩個不同 session），各自從零開始完整建置同一個模組，連對方存在都不知道，直到共用檔案在背景被覆寫才發現。

45. **偵測方式：檔案在自己沒有主動編輯的情況下「自己變了」，而且改動幅度是整個架構級別，不是局部**——本 session 已經成功寫出並執行過 `config.py`／`flag_candidates.py`（跑出數百筆命中），接著分派十幾個純讀寫 batch 檔案的 subagent 去做 L5 審閱（這些 subagent 的 prompt 完全沒提到 `config.py`／`flag_candidates.py`）。過程中收到工具層級的「檔案自上次讀取後已變更」通知，內容顯示這兩支檔案被整個換成另一種設計（資料來源從「posts/comments/group_activity 三分類」換成「personal_activity/group_posts/relationships候選池私訊/group_analysis候選池私訊 四分類」，資料量暴增約 3 倍）。判斷這不是自己哪個 subagent 手滑，而是另一個独立 session 的依據：(a) 自己所有 subagent 的 prompt 範圍都不包含這兩支檔案；(b) 磁碟上同時出現了自己完全没建立過的產出（`data/batches/`「無底線」資料夾，內含 `flagged_1.jsonl`／`reviewed_flagged_1.jsonl` 這種命名慣例，跟自己建立的 `data/_batches/`「有底線」＋`batch_01.jsonl` 命名慣例明顯不同），而且對方已經產出完整的 `reviewed.jsonl`（數百筆，遠超過自己當時的進度）、`report.md`、`report.html`、`cleanup_checklist.html`；(c) 對方覆寫後留下的 docstring 自述「發現另一個獨立 session 覆寫」，等於雙方在互相偵測到對方。
46. **對方即使是善意的，覆寫共用檔案時留下的說明文字也可能把你自己的產出誤植為「對方的東西」，不能照單全收**——本案例中，對方 `config.py` 的衝突說明把本 session 自己建立的 `build_corpus.py`／`posts.jsonl`／`comments.jsonl`／`group_activity.jsonl` 描述成「另一個獨立 session 產生的東西」，但那些其實是本 session 自己在對方出現之前就已建立的檔案——雙方各自只看到「自己知道的部分」，都用自己的視角拼湊出一套「發生了什麼事」的敘事，敘事本身可能局部失真。**收到這類衝突說明時，要對照自己實際的操作紀錄逐項核實歸屬（哪些檔案是自己建的、哪些不是），不能直接把對方的敘事當成事實全盤接受**，但也不要因為對方敘事有誤就整個否定對方的工作成果——本案例裡對方的核心判讀管線品質確實良好（見第 47 點），敘事细節有誤跟工作本身的品質是兩件事。
47. **解決兩份完整但互相衝突的產出，不是「誰先誰留」或「捍衛自己的版本」，而是快速评估品質與範圍後擇一為主、不做覆寫戰**——本案例中兩個 session 的方法論都合理（都是關鍵字預篩→L5 範本化審閱→L6 報告），差異在資料範圍：本 session 版本較貼近 skill 範本字面設計（只掃公開貼文/留言）；對方版本範圍更廣（額外納入候選池模組裡「本人自己發送」的私訊全文，資料量多 3 倍），且對方已經完整跑完 L5（數百筆審閱）＋L6（三份收尾文件都有），本 session 當時 L5 才剛分派出去。核實對方品質的具體做法：抽讀 `reviewed.jsonl`／`report.md` 的判讀理由是否言之有物（不是空泛套話）、有沒有跟其他已知模組的獨立發現互相印證（本案例中對方的核心發現——某年某月的廣告轟炸——與 `group_posts` 模組全量通讀的獨立發現完全吻合，是很強的品質訊號）。確認品質後，**不要回頭用自己的版本覆寫對方**（那只會製造第二輪覆寫戰，且對方已經投入的 L5/L6 工作量遠大於自己），改為：(a) 保留雙方已完成、且彼此不依賴的檔案在磁碟上（本案例是自己的 `build_corpus.py`／三分類 jsonl，僅作範本字面對照用，在 README 裡明講「不是主管線依賴」）；(b) 把自己原本要做但對方沒做的、真正互補的部分做完（本案例是缺的 `README.md`，以及對方報告書裡明確點名「尚未涵蓋」的社團/粉專歸屬掃描）；(c) 在自己補寫的 README／疊代紀錄表裡誠實記錄整個衝突經過，不要假裝自己從頭到尾就是唯一的建置者。
49. **`git commit`（不帶 pathspec）會把整個 index 目前暫存的內容都提交進去，不是只提交自己這次 `git add` 的檔案——多個 session 共用同一個 working directory／git index 時，這代表「別人已經 `git add` 但還沒 commit 的檔案」會被夾帶進自己的 commit**：本案例的真實情況是，完成本模組的 `git add`＋`git commit` 時，另一個完全不相干、負責建置 `reports/`（跨模組彙整報告）模組的第三個獨立 session，剛好已經對它自己的產出跑過 `git add`（但還沒來得及 commit），這批檔案當時就已經留在共用的 git index 裡；本 session 的 `git commit` 沒有加任何路徑限制，於是把 `analysis/output/reports/`＋`analysis/scripts/reports/`（共十來個檔案）一起夾帶進了本次 pr_risk 的 commit——這些檔案本 session 完全沒有寫過、審閱過，commit 訊息裡也完全沒提到。**多 session 共用一個 git repo（沒有各自用獨立 worktree/branch）時，`git commit` 前一定要先看一次 `git status`／`git diff --cached` 確認暫存區裡只有自己這次要提交的檔案，不能假設「我只 `git add` 了我自己的東西，commit 出來的就只有我自己的東西」——commit 提交的是整個 index 當下的狀態，跟這次 session 自己做了什麼是兩件事。發現夾帶已成既定事實（commit 已完成）時，不要用 `git reset`/`git revert` 硬清，那對另一個 session 而言等於自己的工作成果被憑空移除或改寫歷史；如實在自己的任務回報裡揭露「這次 commit 意外包含了非本次任務範圍的檔案」，交由使用者/controller 決定要不要事後拆分。**這是本節第 45-48 點「兩個獨立 session 覆寫同一批檔案」之外，同一場景衍生出的另一種衝突形態——這次不是內容被覆寫，是 git 提交邊界失守。**
50. **兩個獨立 session 各自完成的 L5 質性審閱，即使資料來源、分批方式、甚至判讀用詞（`assessed_severity` 的自訂分類詞）都不同，卻可能各自獨立收斂到同一個具體事實性發現**——本 session 分派的十幾個 batch 審閱 subagent，跟對方 session 的幾個批次，用完全不同的資料切分方式，卻雙方都各自發現「某年某月同一段招募廣告文案被短時間內灌爆數十個互不相關社團」這個具體事件，且都獨立推測出「可能是帳號被盜用/自動發文工具」的成因假說。這是第 28 點「新模組要檢查有沒有跟既有模組重複發現」的加強版案例——這次是連「新模組」都重複了兩次，仍然收斂到一致結論，對這個具體風險事件的可信度是很強的佐證，值得在最終報告裡明確寫出「用兩種完全獨立的方法都得到同樣結論」，而不是只當成兩份重複工作的其中一份丟棄。

## group_posts（社團貼文留言）模組涵蓋率擴充新增坑（2026-09-21，把 Account B 專案 group_posts 模組的訊息量加權涵蓋率從約五成推進到近九成時踩過）

51. **社團貼文/留言模組的「廣播式低敘事價值社團」不能只靠社團名稱關鍵字判斷，要看貼文文字本身有沒有被原封不動廣播貼進多個社團**：候選池排名往後段（本人貼文/留言量體小的社團）幾乎全是「同一則定型文貼進數十個不同社團」的模式——例如「#徵求外幣 #換匯 #面交」這類換匯貼文、「〔某地〕｜全新高質感租屋」租屋廣告、eSIM網卡促銷、「已私訊/已寄信」接案應徵罐頭回覆，這些文字會在完全不相關名稱、甚至不相關分類（`CATEGORY_RULES` 規則式分類常誤判為「其他/未分類」）的社團裡重複出現。判斷方式是把候選池全部內容（用全量通讀，本例約數千行文字）完整讀過一輪、抓出重複出現的定型文樣板，而不是逐一憑社團名稱猜測。這批社團排除後（本例上百個），候選池分母大幅縮小，訊息量加權涵蓋率因此顯著提升——這跟單純「多做幾個候選」提升涵蓋率是兩種機制，前者往往效益更大，因為候選池尾端的廣播貼文社團本來就佔了分母一大塊，但敘事價值趨近於零。
52. **候選池式模組如果過去只維護「排名前 N 大」（`MEDIUM_TIER_TOP_N`）這種單一自動候選清單，擴充到大量「人工逐一判讀後額外挑選」的候選時，要新增一份平行的候選名單（如 `EXTRA_MEDIUM_TIER_GROUPS`）並讓下游全部腳本改吃「自動候選 ∪ 人工候選」的合併結果，而不是每次擴充都手動改 `top5.json` 或繞過 pipeline 直接手寫檔案**：稽核發現這個專案在本次擴充前已經有 18 個候選（排名第 6-22 名）是繞過 pipeline、手動產生 `records.jsonl`/`note.md` 等檔案完成的，`top5.json` 从頭到尾只記錄了前 5 名，之後每次擴充都沒有機制感知「其實已經做到第幾名了」。引入 `EXTRA_MEDIUM_TIER_GROUPS` 這種顯式清單後，`extract_group_posts_targets.py`／`build_group_posts_sentiment.py`／`build_group_posts_reports.py` 三支下游腳本都改成讀取「自動候選 ∪ 人工候選」的聯集，之後新增候選只要把名字加進這份清單、重跑腳本即可，不用再手動繞過 pipeline 產生檔案。
53. **驗證腳本抓到的「語錄找不到對應原文」失敗，第一個要懷疑的原因是「把另一個候選的內容誤植進這個候選」，尤其是平行處理多個小量體候選時**：本次同時處理二十多個新候選（多數量體僅個位數到十幾則訊息），寫作時人工從已讀過的內容裡挑語錄，其中一個候選（Group P，某大學科系社團）的其中一則「主動提供協助」的語錄，其實是另一個內容相近的候選（Group Q，設計職涯互助社團）裡真實存在的語錄，兩者主題都是「回應同學的作業/面試互助需求」，內容相似度高導致人工挑選時記錯歸屬。`verify_quotes.py` 精準抓到這筆（因為該候選自己的 `records.jsonl` 裡根本沒有這句話），修正方式是回頭核對該候選自己的原始 `records.jsonl`、換成真的屬於這個候選的語錄，而不是猜測是格式問題。**同時處理多個內容相似的小候選時，這種「跨候選誤植」比單一候選內「意譯/截斷/拼接」更容易發生，也更難靠肉眼複查抓到（因為誤植的語錄本身讀起來完全合理、語氣也吻合），驗證腳本仍是唯一可靠的防線。**

## 風險模組專屬

14. **關鍵字/正則預篩一定會漏（也會有假陽性）**：反諷、暗語、委婉說法都可能漏掉；同時關鍵字命中不等於真的有問題。標準做法是「預篩出候選 + 對「沒被篩到」的內容做分層隨機抽樣」一起交給後續判讀，不要只信賴預篩結果本身，也不要把預篩命中直接當成最終判定。
15. **嚴重度排序是查表，不是判斷**：預篩腳本目前只用固定優先順序把命中類別分組排序，這只是「怎麼呈現」，不是真正評估每一項的實際風險程度——這正是為什麼風險模組需要補上真正的 L5 範本化判讀（見 `程式\風險\範本\審閱判讀.md`），而不是停在預篩+排序就當作結案。
16. **語料涵蓋未成年時期的內容，嚴重度判讀要用當時年齡的標準，不能比照成年人公開發言**：帳號活躍期若橫跨國高中（未成年）階段，青少年間的鬥嘴/玩笑/中二發言，若比照成年人正式場合發言的標準判讀嚴重度會系統性高估風險。判讀前先確認目標的年齡/人生階段分佈（可查 `personal_activity`/`relationships` 既有分析），對未成年時期內容明確調降嚴重度權重，`審閱判讀.md` 範本目前沒有這條，建議之後補上。
17. **社團/粉專「名稱」關鍵字比對（歸屬掃描）一樣會有假陽性，且比內容關鍵字更容易誤判**：一個真實案例，某個測驗類 App 的地區版粉專（名稱格式像「〈App 網域〉 中國」）名稱裡剛好帶有「中國」二字，被 `political_social` 關鍵字群誤判為政治性粉專，但實際只是應用程式的地區後綴，跟兩岸政治毫無關係。名稱型關鍵字比對比內容型更容易誤判，因為名稱通常很短、缺乏上下文可供判斷語意，人工複核時要特別留意這種「詞面命中但語境無關」的情況，不要看到命中就直接列為風險項目。

## L6 報告產生器新增坑（2026-09-21，Account A 專案「dashboard 有些頁面打不開」回報，追查後發現是產生器模板裡的相對路徑深度算錯）

54. **report.html 模板裡的 `"../.."` 這類相對路徑是手算的，輸出檔案的巢狀深度只要跟模板作者心算的不一樣，就會整批產生壞連結，而且產生腳本本身完全不會報錯**：Account A 專案裡兩個獨立產生器都踩了這個坑——`分析\scripts\relationships\build_report.py`／`build_report_deep.py` 產出的 `output/relationships/quant/<slug>/report.html` 實際巢狀在 output 底下第 3 層，模板卻只寫 `../../assets/shared.css`（少算一層），數十個聯絡人的 quant 頁面因此 CSS／Chart.js／首頁導覽／回列表連結全部失效；`分析\scripts\messages\build_derived_and_report.py` 產出的 `output/messages/report.html` 連到 `derived/messages_by_person|group/<slug>/chat.html`（`derived/` 跟 `analysis/` 同層，不在 `analysis/output/` 底下），模板同樣少算一層，數百筆聊天存檔連結全部 404。兩個 bug 都是同一種模式：**只要新增或修改任何 report.html 產生器，輸出後一定要用 `程式\共用\verify_links_template.py <output 根目錄>` 掃一次，不能只靠人工點幾個連結「看起來正常」就判定沒問題**（人工點擊很容易漏踩到壞的那幾個，尤其 CSS/JS 資源載入失敗時頁面通常不會明顯報錯，只會「樣式跑掉」，使用者不會馬上聯想到是連結路徑錯誤）。這支驗證腳本應該跟 `verify_quotes_template.py`／`verify_coverage_template.py` 一樣，是任何 L6 產出在交付前的必跑項目，不是選配。
55. **同一個 report.html 模板可能被指派給兩批粒度不同的來源資料，模板寫死欄位名稱時要考慮這個情況**：`relationships` 模組的中量報告產生器 `build_report.py` 原本假設每個人的 `feature_matrix.csv` 都是「年」粒度（有 `year` 欄），但深量分析會把同一個人的 `feature_matrix.csv` 升級成「月」粒度（欄位變成 `month`，格式如 `2016-04`），而深量目標同時也還留在中量目標清單裡（中量清單是深量清單的超集，深量只是「額外再做更細的分析」，不是取代），導致中量產生器讀到月粒度檔案時對不存在的 `year` 欄位直接 `KeyError` 而整批中斷。修法是讓讀取端同時支援兩種粒度（偵測欄位存在與否，月粒度時用 `month.split("-")[0]` 彙總回年度），而不是假設每個目標的資料格式都跟清單類型一一對應。

## 跨帳號身分查證新增坑（2026-09-21，Account A／Account B 跨帳號比對第二輪擴充——Person X 全文通讀、數十位候選 note.md 全文查核時踩過）

56. **候選人 note.md 的「方法與限制」段落可能藏有前一位 agent 主動留下的跨帳號交叉引用，只看敘事段落／摘要層級核對容易漏掉**：一個真實案例，Person Y 的 note.md 早就在「方法與限制」段落寫了明確指向 `personal_activity/notes/note.md` 的「重要交叉參照」文字，但因為跨帳號綜合文件先前只做 README 摘要層級核對（沒有逐篇讀 note.md 全文），這條已經寫得很清楚的線索被整整跳過一輪。**教訓**：跨帳號／跨候選排查類任務，除了讀 note.md 的敘事本文，也要特別留意「方法與限制」「已知限制」這類段落裡的「交叉參照」「另見」字樣——這是前面處理過的 agent 主動留給後人的路標，比自己從零開始重新發現線索便宜得多，不應被摘要層級核對忽略。
57. **同一個跨帳號人物可能被多篇不同候選人的 note.md 各自零散提及，單篇讀不出規律，要在讀完全部候選後做關鍵字回顧**：本案例中，Person P 與 Person Q 兩篇互不相關的 note.md，各自獨立提到已確認跨帳號人物 Person Z（一篇在對話裡直接喊出 Person Z 的全名，另一篇只用名字後兩字提及暑假到對方家聚會）。這種模式必須在讀完一批候選人的全部 note.md 之後，回頭搜尋「已確認／高度推測跨帳號人物的全名、簡稱、暱稱片段」（本案例是 Person Z 的全名、名字後兩字，以及 Person Y 的名字後兩字）才會浮現，逐篇單獨判讀時看不出彼此的關聯。
58. **確認跨帳號人物在對方帳號側是否存在對應資料時，不能只 Glob 同名的一對一對話串資料夾——很多人際互動只以動態時報留言／按讚形式存在**：即使某人是已確認的跨帳號共同聯絡人（如 Person Y、Person Z），Account B 側 `relationships/quant/` 底下也未必有同名資料夾——這批人常常只透過貼文留言／按讚跟本人互動，從未建立獨立 Messenger 對話串。查證時應優先看 `personal_activity/notes/note.md`（個人動態貼文與留言的質性分析），而不是只搜對話串資料夾名稱，否則會誤判為「查無資料」而漏掉真正存在的證據。
59. **Account B 側 `derived/messages_by_person/.../chat.html` 是「報表外殼＋單行 HTML blob」混合結構，不能直接用 Read 工具當純文字讀**：檔案開頭有大量 CSS／統計卡片／圖表容器的 HTML（前數千字元），乍看像空殼報表；真正的逐則訊息壓縮在 `<div class="msg-list">` 底下、完全沒有換行的單行 HTML（`<div class="msg msg-self">...</div><div class="msg msg-other">...</div>...`），必須用正則表達式抓 `msg-meta`／`msg-body` 才能還原成可讀對話，直接用 Read 工具看只會看到一整行數十 KB 的 HTML。另外，這類檔案的 `<title>` 顯示亂碼不代表整份檔案編碼有問題——`<meta charset="UTF-8">` 通常是對的，用 `encoding='utf-8'` 讀取後中文內容完全正常，亂碼只是報表產生器 title 欄位本身的既有小 bug，不必因此懷疑匯出檔案損壞。
60. **判斷兩個帳號是否為同一人時，「對方怎麼稱呼本人」比對日期巧合更直觀、成本更低**：一個真實案例，Person X 在 Account A 側用舊帳號名稱的縮寫／暱稱稱呼本人，換帳號後在 Account B 側同一段對話裡交替使用舊暱稱與新帳號名稱（以及新帳號名稱的諧音暱稱）——這種「新舊暱稱混用」的訊號辨識度很高、掃描成本很低（純文字搜尋即可），比對照 `friend_since` 是否落在已知換帳號日期簇更容易一眼判斷「這是同一人」。建議跨帳號人物比對時，除了查日期，也主動掃一遍訊息文本裡「對方怎麼稱呼本人」，看新舊暱稱是否混用。
61. **共同群組聊天記錄本身可能藏有比一對一對話更直接的身分切換證詞，值得優先讀**：一個真實案例，Account A 側某個同學群組在帳號轉移當天晚上的系統訊息直接寫出「〔某成員〕將 Account B 加入了群組」（旁觀者視角保留了本人真名），本人隨即在群組裡用玩笑口吻說明新帳號就是自己——這段對話比任何一對一對話裡的間接旁證都更直接，且時間點與官方帳號註冊時間戳幾乎同時。**教訓**：查跨帳號身分證據時，不要只鎖定一對一對話串，兩邊共同群組的系統事件訊息（成員異動、旁觀者視角保留的真名）與現場閒聊往往藏有更直接、更難偽造的證詞，值得優先排查。
62. **PowerShell 讀取中文內容檔案務必明確指定 UTF-8 編碼，否則字串在記憶體裡就已經壞掉**：`Get-Content -Raw` 或直接印到主控台若沒指定 `-Encoding`／`[System.Text.Encoding]::UTF8`，中文會被依系統內碼頁讀壞成亂碼，而且是「記憶體裡的字串已經壞掉」而非單純顯示問題——即使之後把這個壞掉的字串寫成新的 UTF-8 檔案，用其他工具（含 Read 工具）打開一樣是亂碼。正確做法是 `[System.IO.File]::ReadAllText(path, [System.Text.Encoding]::UTF8)` 讀、`[System.IO.File]::WriteAllText(path, content, [System.Text.Encoding]::UTF8)` 寫。一個真實案例曾因此一度誤判「Account B 側 chat.html 本身內容壞掉」，後來才發現是 PowerShell 讀取環節的問題，Grep 工具讀取同一份檔案完全正常。
63. **同一個人在專案裡兩個模組「對不上」，先查兩邊的前置過濾門檻，別急著懷疑姓名正規化**：一個真實案例，Account B 側某位聯絡人 Person W 在 `friends_insight`（好友清單，找得到）與 `relationships`（候選池，找不到）兩個模組裡對不上，查證後發現兩邊姓名比對邏輯其實一致，真正原因是 `relationships` 域的 `build_thread_ranking.py` 有 `MIN_MESSAGE_COUNT_FLOOR=10` 候選池門檻、`friends_insight` 域沒有（且刻意保留低量體「沉默好友」分類）。以後遇到類似「模組A找得到、模組B找不到同一人」的情況，第一步先讀兩邊腳本開頭的 `config.py`／篩選條件（floor、exclude list、is_group/likely_spam 之類的前置排除），這通常比姓名正規化問題更常見、也更好查證。
64. **Account B 專案有兩個並存的目錄，查證跨模組問題前先確認腳本實際放在哪個目錄**：`<account_B>\extracted\`（含完整 `raw/`，`relationships` 域腳本放在這裡）與 `<account_B>\<export_folder_YYYYMMDD>\`（沒有 `raw/`，但有自己的 `analysis\pipeline\` 目錄，`friends_insight` 域腳本放在這裡）是兩個獨立目錄，各自有一份內容應一致（但未逐位元組比對過）的 `thread_ranking.jsonl`。對錯地方查證會浪費時間或得出錯誤結論。

## 候選池尾端大規模平行初篩新增坑（2026-09-21，Account A 關係模組候選池排名尾段數十人分 4 批平行 agent 初篩、好友清單數十人交叉比對時踩過）

65. **候選池排名機制會把「本人單方面連續留言、對方完全零回應」的 thread 也排進候選池——先掃 sender 分佈比逐則讀語意更快**：真實案例 Person V（十幾則）全部 sender 都是本人，對方自始至終零回覆，且多則是無意義重複字元。這類「假雙向對話」會被訊息量/跨度計分的候選排名誤判為值得分析的候選。建議初篩時先掃一眼 thread 內 sender 是否只有本人一種，若是可直接判定排除，不必逐則細讀語意。
66. **同樣是「單日遊戲相關對話」，區分「純物流溝通」與「有個人色彩」的實用標準是有沒有夾雜自嘲/生活自述/玩笑鬥嘴等性格片段，即使主題仍是遊戲**：真實案例對照——Person R、Person S 只有ID/路線分工等純物流資訊，判定排除；Person T 有「我也是剛轉職的新手 orz..」這類自嘲、Person U 有「你被扁了」「別鬧了」的鬥嘴，即使主題同樣是揪團/組隊，仍判定為真實可寫的關係並納入分析。這條界線 `config.py` 排除註解目前沒有明講，只能從既有案例反推，之後遇到邊界案例可參考。
67. **候選內容本身通不過初篩，不代表這個人名跟姊妹專案已確認人物的關聯就沒有記錄價值**：真實案例 Person N（候選池裡一個獨立 1:1 對話串，跟已知同名重要人物是否同一人待查）內容本身過於單薄被排除，但把「已核對跨帳號分析文件、確認 thread_id/訊息數與該文件引用的候選池紀錄完全一致、但內容本身不足以獨立成立」這個查證結果寫進 `config.py` 排除註解裡，比只寫「內容過少」更有價值——能避免未來重複查證同一個問題。
68. **兩邊專案的 `chat.html` 模板可能不同版本、用同一段正規表達式解析會在其中一邊靜默得到空結果**：Account B 側用較新模板（`class="msg-body"` 區塊＋獨立 `sender`／`ts` span），Account A 側用較舊模板（`<div class="msg">` 內聯 `class="ts"`／`class="sender"`／`class="body"`）。只寫一種解析邏輯會導致其中一側訊息「讀不到」卻不報錯（regex 找不到就回傳空字串），容易誤判為「無內容」。要同時支援兩種格式，或先探測模板再解析。
69. **CJK 近似變體字會讓「同一人名」字串比對失敗，跨文件核對前務必核對原始資料裡的確切字元**：真實案例（以下用虛構姓名示意），文件手寫的「王彥明」用的是「彥」（U+5F65），但原始資料 `friends_join.jsonl` 裡實際存的是「王彦明」的「彦」（U+5F66，形近但碼位不同的變體字）。用文件裡手打的排除清單去比對原始資料時必須先核對實際資料裡的確切字元，否則排除名單會漏掉本應排除的人，或誤判為「新發現」。
70. **Windows Git Bash 下 Python 預設用 cp950 編碼寫 stdout，一遇到生僻 CJK 字元就會整個腳本崩潰**：批次處理大量含中文人名的資料時，務必讓腳本直接以 `encoding="utf-8"` 寫入檔案，不要依賴 `print()` 到 console，否則可能在處理到一半時中斷、且從失敗訊息不容易一眼看出是編碼問題還是邏輯錯誤（另見已知坑：本 skill 通用 Python 腳本一律在檔頭包 `sys.stdout = io.TextIOWrapper(...)` 這個既有慣例，就是為了避免這個問題，新寫的一次性腳本也應該比照）。

## 候選池排除清單擴充新增坑（2026-09-21，Account A group_posts 模組候選池尾端數十個廣播垃圾/小型社團批次初篩時踩過）

71. **協調者用文字分隔符號（如「｜」）人工列出一批候選名稱交給 agent 時，若某個候選本身的名稱就含有那個分隔符號，會被錯誤拆成好幾個不存在的假名稱**：真實案例，協調者用「｜」分隔候選清單，但其中一個社團全名本身就是「〔某某〕城｜出金心得｜玩家交流區」這種格式（含兩個｜字元），照協調者原文切分會拆成 3 個不存在的假名稱，導致 3 條排除規則永遠比對不到、真正該排除的社團漏網。收到這類清單時，應先跟原始資料檔案（例如 `all_records.jsonl` 的唯一 `group` 值集合）交叉比對，而不是單純照分隔符號機械切分。
72. **候選名稱含非中文變音符號（越南文、法文等）時，Unicode 正規化形式（NFC vs NFD）可能跟原始資料不一致，導致字串比對沉默失敗**：真實案例（社團名稱以虛構的「Hội Những Người Bạn Cũ」示意），社團名稱含越南文變音符號，協調者訊息裡貼的文字是 NFC 正規化（組合字元），但原始 `all_records.jsonl` 裡實際存的是 NFD 正規化（字母+變音符號分開兩個 codepoint）——兩者螢幕顯示完全相同，但 Python `==` 判定不相等，排除規則寫進去後永遠不會命中、且不會有任何報錯提示。跨語系（越南文/日文/法文等含組合字元的語言）名稱要寫進排除清單時，務必直接從資料檔案本身取字串（例如寫小腳本從 JSONL 讀出原始 bytes），不要從對話文字手動轉錄。
73. **任務描述裡「這個候選已經有完整分析」這類前提陳述，可能是任務指派者自己記錯或推測，交付前務必實際查證，不能照單全收**：真實案例，協調者派工時以為某個以班級命名的 Messenger 群組已有完整深層分析，agent 實際 `ls` 對應資料夾後發現它只是候選排名表裡一筆被 `excluded_reason: "too_many_participants"` 排除的候選，從未真正跑過分析。遇到這類「已存在」的前提描述，第一步永遠是去對應資料夾實際確認 `note.md`／報告檔案是否存在，不能只憑名稱相似或任務描述的字面陳述就假設屬實。
74. **判斷一筆紀錄「有沒有文字內容」不能只看 `text` 欄位是否為空，要連同 `header`／事件類型欄位一起看**：真實案例，兩筆 `admin_action`（改名事件）紀錄乍看 `total_text_count=0`（貌似無文字），但 `text` 欄位其實被填成「改名後的新社團名稱」（不是空字串），要看 `header` 欄位才知道這是一筆改名事件、不是真人發言，單純用 `text` 是否為空判斷「有沒有內容」會誤判其性質。
75. **協調者手動彙整的統計表格數字，可能跟資料檔案裡精確比對出的實際筆數有落差，以自己重新核對的數字為準，不用回頭追查表格數字的來源**：真實案例，協調者提供的任務表格寫某候選「1筆」，agent 用程式精確依 `group` 欄位比對後其實有 4 筆——推測表格只計算了 `kind=post`、沒算 `admin_action`／`comment`。這類表格數字是給任務範圍參考用，不是要驗證的黃金標準，發現落差時用自己重新比對出的精確數字繼續往下做即可。
76. **多個 agent 平行處理「相似但不同」的候選批次時，可能各自獨立踩到同一組候選名稱，事先讀一次共用檔案現況可以避免重複勞動**：真實案例，兩個 agent 分別被指派不同批次的社團候選，但某人力銀行社團、某貸款理財社團這兩個名稱因為內容判讀結果相同（同一組廣告文案），被其中一個 agent 排除後，另一個 agent 動手前重新讀取 `config.py` 才發現已經被排除，及時避免了 Edit 工具對同一個 set 字串重複追加。這印證了先前已知的「動手改共用檔案前先重讀最新版」原則同樣適用於發現「這個候選是不是已經被別人處理過」，不只是避免編輯衝突。
77. **只憑「名稱＋筆數」層級做的稽核判斷，即使結論寫得再篤定，也可能被後續逐字讀完內容的結果推翻——量體過低不等於沒有敘事價值**：真實案例，`group_posts` 模組先前一輪稽核（2026-09-18）逐一看過剩餘數十個候選的**名稱與筆數**後，判定「候選池已到達實務上的擴充上限，沒有更多真實內容值得個別中量分析」。但 2026-09-21 兩個 agent 真正逐字讀完這批候選的**實際內容**後，發現其中 3 個「量體過低」（1-2 筆）的候選其實是真實個人內容（本人親手建立的社團、帶有個人資訊的留言、帶個人喜好色彩的留言）。**教訓**：「這批候選量體太低，應該沒什麼好寫的」這種只看統計欄位（筆數/名稱關鍵字）就下的稽核結論，本質上是一種未經驗證的猜測，不能取代「逐字讀完內容」這個唯一可靠的判斷依據——即使是 1 筆紀錄，也可能承載重要的個人訊息（本文範例：親手建立一個社團這個行為本身就是敘事）。如果稽核只用統計欄位判斷「不值得再做」，應該明確標註「未逐字讀過內容，僅依名稱/筆數推測」，不要寫成篤定的最終結論，避免誤導後續（包含自己）省略掉真正該做的通讀步驟。

## 跨帳號資料合併進同一份 L6 報告新增坑（2026-09-22，Account A 專案把姊妹專案 Account B 的逐年活動量與跨帳號敘事整合進既有 `reports/life_timeline.html` 時踩過）

這一節是新的模式：前面第 56-64 點都是「用姊妹專案的資料來查證身分」，這裡則是**把姊妹專案既有產出真的讀進本專案的報告產生腳本、當成報告的一條資料線**（同一個人被帳號轉移切成兩半的人生，拼回同一張圖）。做法本身可行也值得複用，但有三個必踩的坑。

78. **跨專案讀取要當成「單一具名例外」處理，不要順手破壞既有 `paths.py` 可攜式慣例**：可行做法是在報告腳本裡宣告一個**唯一**的模組級常數（例如 `SISTER_YEARLY_STATS_PATH`），上面用註解寫清楚三件事——(a) 為什麼這個路徑非寫死不可（姊妹專案是獨立倉庫，不在 `PROJECT_ROOT`/`RAW_ROOT`/`DERIVED_ROOT` 之下，沒有相對路徑可用）、(b) 這是本檔案／本專案唯一一處這樣做的地方、(c) 只讀哪一支檔案、不觸碰姊妹專案其他任何檔案（姊妹專案務必維持唯讀，收工前用檔案 mtime 掃一次確認真的零寫入）。讀取函式本身要對「檔案不存在」優雅降級（`if not path.exists(): return {}`），因為姊妹專案可能不在這台機器上，不能讓別人重跑本專案的報告時整支腳本崩掉。
79. **兩邊同名模組的 JSON 欄位不會一致，加總公式要各自對照自己的 schema，不能照抄**：真實案例，Account A 側 `personal_activity/data/yearly_stats.json` 的活動量是 `post+comment+photo`，Account B 側同一支檔案**沒有 `photo` 欄位、但多了 `story`**（限時動態），照抄 Account A 側公式會靜默少算一整類內容（`v.get("photo", 0)` 永遠拿到 0，不會報錯）。動手前先把兩邊 JSON 的 key 印出來逐一對照，並把「這邊用的是哪個公式、為什麼跟另一邊不同」寫進函式 docstring。另外，兩邊對「零活動年份」的處理慣例也可能不同（省略該年 key vs 寫入 0）——省略式的要讓呼叫端 `.get(y)` 拿到 `None`、圖表用 `spanGaps:false` 斷線，不要用 `.get(y, 0)` 把「沒有資料」偽裝成「活動量為零」。
80. **手寫的跨帳號綜合文件是二手來源，它的逐字語錄與「唯一／同時／全篇只有一處」這類全稱判斷都要回頭對一手資料重驗，不能當成已驗證事實引用**：兩個都真的發生過的失誤——(a) **語錄被二手來源截斷**：綜合文件引用某則代理人訊息時停在句號（看起來是完整一句），一手 `relationships/quant/<slug>/messages_full.jsonl` 原文後面其實還有一句，照抄二手來源等於繼承了一次沒標註的截斷（`verify_quotes` 類腳本用子字串比對仍會 PASS，抓不到這種「引用了真實存在的前半段」）；引用時務必回到一手 jsonl，並把出處寫成一手檔案路徑＋seq／時間戳，不要只標綜合文件或 `note.md`（`note.md` 常只摘了語錄的一小段）。(b) **全稱判斷是錯的**：綜合文件寫「某個 5 人小群組是全篇唯一能看到兩個帳號名字同時在場的地方」，但用腳本掃過本專案 `derived/messages_by_group/*/chat.html` 全部群組、逐群統計兩個帳號各自的發言數與起訖日期後，實際上**有四個群組**同時出現兩個名字；更關鍵的是，那個被說成「同時在場」的小群組其實是**前後接棒**（舊帳號止於轉移前約一個月、新帳號從轉移當天才開始，完全不重疊），真正有時間重疊的是另外兩個群組（舊帳號在轉移後還繼續發言好幾個月）。**教訓**：任何「唯一／只有一處／從未重疊」的全稱句，成本最低的驗證方式就是寫五行腳本把全部候選檔案掃一遍、按發言者統計筆數與 min/max 日期，不要因為二手文件寫得篤定就直接寫進報告；發現出入時，在報告裡明講「此處以一手逐則資料實查結果為準，與綜合文件說法有出入」，並回頭在綜合文件補更新註記。
81. **跨帳號敘事整合段落要把「事實」與「推測」分層標註，且分層界線要自己重新判斷一次**：把兩個帳號的資料拼成同一條人生敘事時，一定會混入推論（例如「集中重加好友代表本人在新帳號把舊親友加回來」）。可行做法是在報告段落裡明確分成「已確認的事實」（有官方系統紀錄／逐字語錄／系統欄位支撐）與「交叉比對後的合理推測」（多條弱證據收斂）兩個小標，事實層每一句都要能指到一手檔案。順手要核的細節：事實層的日期窗口別被推測層的概述帶壞——真實案例，敘事寫「親友的 `friend_since` 全部落在帳號轉移當天那一兩天（D 日／D+1）」，但其中一位親屬那筆其實是 D+2，正確寫法是「D～D+2 這三天」並逐人標出各自日期。

## 單一程式碼重構後的多批補強新增坑（2026-10-01；細節見 `查證與協作.md`、`PR審閱.md` 與 `social-export-analysis` 的 `references\`）

這一節的專案已經把多份舊程式碼合併成一份，兩個帳號共用。坑大多發生在「質化筆記已經寫完，回頭查證或補強」的階段。以下例子都是虛構的。

82. **抽樣時期寫的筆記不能直接當結論來源**：語意複查時，一批四十多篇抽樣期的筆記幾乎每篇都要修。寫進知識庫或報告前，先確認來源是全讀版；抽樣版要先全讀重寫，或逐句回 L1 查證。見 `查證與協作.md` §1。
83. **文字欄只有「IP 位址」的訊息，是本人傳的讚貼圖或相片**：讀成系統通知，就會寫出「本人未回覆」這種反向結論。曾經一次要修三十多篇。判讀時看 L1 的 `type`／`media`；拿去給 LLM 讀的摘錄，先把這類訊息換成「〔貼圖〕」「〔相片〕」。
84. **事件日期要換成當地時間**：匯出檔是固定時區，國外發生的事件在午夜前後最容易錯一天，例如交往日、告白日。
85. **範本字句和 Meta AI 的回答會被算成本人發言**：例如「你已開始通話」、Marketplace 預設詢問句、Meta AI 的回覆。不能當語錄，不能寫成「本人說」，也不能拿來算本人發了幾則。
86. **「斷聯」先查是不是換帳號**：同一個人在另一份匯出裡可能一直有聯絡。同一個專案就有三篇以上把換帳號寫成了斷聯。
87. **帳號與時期混淆**：資料夾照匯出分，不代表訊息是那個帳號發的；舊帳號換帳號後還可能發訊息（交易、借給別人、被盜）；本人的英文暱稱可能剛好等於某個帳號名。寫「某帳號做了什麼」要用發言者別名算出來的數字。完整規則見 `social-export-analysis` 的 `references\multi-account.md`。
88. **兩份匯出都有的共同串要扣重複、只分析一次**：兩邊的候選排名都要跳過鏡像串，不然「下一批候選」最前面幾個都是已經做過的。人數上限排除掉的可能剛好是比較完整的那一側，要記下哪段期間沒有讀到。
89. **PM agent 和使用者的數字一樣要回 L1 查證**：曾經發生日期切點多算一天，數字多出約兩成。見 `查證與協作.md` §2、§3。
90. **使用者的說法跟資料衝突時**：兩邊都查，照實回報成立的部分和不成立的部分；資料判斷不了的才問使用者。不要跟著使用者的語氣翻盤。
91. **PR 審閱要逐筆做，附錨點**：散文報告沒辦法驗證，也沒辦法做成清理清單。洗版內容可能是帳號被借用，成因要問使用者。測試例句不能用資料裡的真實地址或電話（曾經因此進了 git 歷史）。見 `PR審閱.md` 與 `social-export-analysis` 的 `references\privacy.md`。

## 第二輪補強新增坑（2026-10-01；細節見 `查證與協作.md` §6、§7、`PR審閱.md` §4b 與 `social-export-analysis` 的 `references\`）

92. **使用者填清單的方式跟回寫腳本預期的不一樣**：使用者在段落標題寫「全部都是」，每列欄位空著，腳本只讀每列的欄位，dry-run 顯示變更 0 筆、全部略過；轉成答案檔帶入後才正確寫入。回寫一律先 dry-run 看會改幾筆，0 筆就是警訊。見 `查證與協作.md` §6。
93. **使用者確認要能覆蓋規則判定，而且要有「不同人」這一級**：否則已經確認過的人，下次規則一跑又被打回「僅同名」，也沒辦法表達「確定不是同一人」。見 `查證與協作.md` §6。
94. **同一群組的成員名單本身就是跨帳號證據**：群組要用穩定的 thread 編號加逐字相同的訊息來對，不能用群組名。曾經因為把同一群組誤判成兩個群組，有好幾位被低估。見 `social-export-analysis` 的 `references\multi-account.md` §7。
95. **抽樣寫成的大型對象，先做 strict 引文驗證**：改前只過約七成，修完推翻了兩句結論。strict 不能證明敘事正確，全讀前不寫新結論進知識庫。見 `查證與協作.md` §7。
96. **範本字句的規模可能比估計大幾百倍**：估計幾十則，實測兩萬多則。先唯讀試算再決定修法；改成「只加旗標、分析時用 is_typed()」，`message_count` 的口徑不動。見 `social-export-analysis` 的 `references\pitfalls.md` §C1。
97. **使用者確認成因後，只改寫錯成因的句子**：判定和清理建議不變；同一段期間的其他內容要分開確認；不改的舊文件要列在勘誤的「原文位置」。見 `PR審閱.md` §4b。
98. **大量改寫筆記、重抽資料、git gc 會被自動模式的權限分類器擋下**：要使用者親口放行，再由主線親自執行，或在新 agent 的初始 prompt 開頭放一段「使用者授權（原話）」（已驗證一次：新 agent 全程沒被擋；用訊息轉給正在跑的 agent 則會被擋）。不能讓 agent 自己繞過。

## 全面優化輪新增坑（2026-10；細節見 `查證與協作.md` §8～§10、`人生時間軸.md` 與 `social-export-analysis` 的 `references\`）

99. **新寫的敘事錯誤率很高，一律派第二個 agent 做語意複查**：補讀後的新筆記抽查約 40 句錯近四分之一，新寫的時間軸事件錯約三成。strict 驗證和覆蓋檢查都抓不到。見 `查證與協作.md` §9。
100. **舊驗證只比到分鐘、還先去空白，所以全過**：改用共用 strict 驗證器後抓出數百筆，多數是秒數抄錯、抄進心情尾巴、只差空白。先唯讀盤點，再只修可以機械修的。範本：`程式\共用\quotes_strict_template.py`。見 `查證與協作.md` §8。
101. **正文引號可能有幾千處，要用登記制**：術語登記在 `inline_terms`，引別串的登記在 `inline_source`，沒登記又不是逐字的印 WARN。抽樣處理約一成漏判，最後改成全量處理。見 `查證與協作.md` §8。
102. **人生事實和時間軸**：只收確定和高信心的，衝突的等使用者確認；換成當地日期；回報日不是發生日；兩個帳號互傳的信件是草稿，不是已寄出；居住時段用登入國家逐日核對，再參考機場、航班訊息切開。見 `人生時間軸.md`。
103. **修正工具要預設 dry-run，而且只有唯一候選才寫**：流程是 scan → 判定檔 → dry-run apply → 備份後寫入 → 自我檢查。見 `查證與協作.md` §10。
104. **筆記裡可能直接寫了第三方電話**：要靠個資掃描接進 verify 來防，測試例句連街名都要用虛構的。見 `social-export-analysis` 的 `references\privacy.md` 與 `scripts\pii_scan_template.py`。
105. **agent 回報說「使用者說了某句話」，要能追到原話**：主線的對話裡看不到的話，就當作未查證。跨 session 的訊息可能要使用者核准才送得到，不要卡在等回覆。見 `social-export-analysis` 的 `references\parallel-agents.md`。

## 長尾全讀批新增坑（2026-10；細節見 `查證與協作.md` §11 與 `social-export-analysis` 的 `references\pitfalls.md` §E、`parallel-agents.md` 長尾段）

106. **錯誤率要靠校準閘門和會長大的共同規則壓下來**：第一批人物、第一批群組先各自複查，錯誤類型立刻補進共同規則。這樣做以後，事實錯誤率從兩到三成降到 5% 以下。最常犯的錯是把「A 說 X，B 回 Y」的順序壓錯。
107. **通話紀錄的時間是結束時間**：開始時間要用紀錄時間減掉通話時長。夏令時間一年切換兩次，要用有地區名稱的時區換算，一句話摘要裡的日期也要換。
108. **只有心情回應的訊息會被算成對方打字**，對方整串空白多半是匯出缺漏。所以對方的打字數、「誰先開口」都可能偏多。內容看不到就寫看不到，不要補內容。
109. **「我們」不等於本人**：主詞是「我們」或「We」的話，不能拿來證明本人做過某件事。本人傳的連結也不等於本人的作品。
110. **事實查核：判斷「L1 沒有」之前先全文搜尋**；佐證要看那一則在回答什麼問題；「清單」不等於「選定」。

## 結案寫入新增坑（2026-10；細節見 `查證與協作.md` §12）

111. **中間表的日期是匯出時區**：從勾選表或查核紀錄抄日期寫進知識庫、家族時間軸時，要再換一次當地時間。前面每一輪都提醒過，回填時照抄還是會錯。
112. **看得到的時間點不是發生日**：「對方說已經收到通知」的那天不是寄出日；L1 沒寫的細節和日期就寫「私訊沒寫」，不要補。
113. **單次事件、角色詞、成交**：只出現一次的做法不寫成規則，「組長」「被加入」「賣過」要有系統事件或原話才寫。
