# 自然語言問答與隨選執行

原專案是批次架構（先跑排名，一次處理固定 top-N）。本 skill 的預設互動模式是隨選：依問題判斷最小必要步驟，只跑真正需要的部分，並且優先直接在對話中回答，而不是強制寫檔。

## 決策表

| 問題形狀 | 實際會跑的步驟 |
|---|---|
| 簡單事實/近況（「最近有沒有聯絡」「這是誰」） | 解析對象 → 查快取 → 有快取直接讀 quant 摘要＋最近的摘錄；沒快取且問題夠簡單，可以直接讀該對象的原始聊天記錄尾端，不用跑完整 pipeline |
| 關係品質/趨勢問題（「是不是變冷淡了」「溝通模式如何」） | 解析對象 → 確保（沒有就現建）該對象的語料＋特徵＋摘錄 → 讀 quant 摘要＋摘錄後直接在對話中回答，不寫筆記檔 |
| 聚合問題（「我最近的人脈狀況」「有什麼PR風險」） | 現跑一次該模組的候選排名（純 JSON、便宜）→ 回答 top-N 表格＋一行說明，不對個別對象做語料/特徵建置，除非使用者接著追問特定對象 |
| 群組問題（「這個群組是不是交易性質」） | 解析對象 → 確保群組語料＋特徵 → 若模組有 L5，跑質性判讀範本 → 回答，主動提及該模組已知的坑（例如群組模組沒有具名提及比對） |
| 明確要求「寫完整筆記」「建 dashboard」 | 次要路徑：走該模組完整的批次寫檔流程 |

單一對象問答時，批次架構裡的深/輕分層意義消失（分層是為了控制多目標的成本），一律用深層粒度處理；分層規則只在使用者明確要「整批」時才套用。

## 實體解析

用問題裡的姓名/群組名去模糊比對 `thread_index.json` 的 `name` 欄位（不是 L3 的嚴格雙清單比對，那是給結構化 join 用的）。多個候選都合理匹配時，列出候選（名稱、訊息量、時間範圍）請使用者選，不要靜默選訊息量最高的那個——這跟「絕不悄悄合併」的姓名比對哲學一致。實作見 `程式\共用\resolve_entity_template.py`。

## 快取/新鮮度機制

這是本架構裡唯一真正的新工程，不是照抄現有邏輯——設計與測試都要認真對待。

索引檔：`analysis/output/social_export_insights/cache_index.json`，按 `模組/對象 slug` 記錄：
```json
{
  "module": "relationships",
  "target_slug": "...",
  "thread_id": "...",
  "message_count_at_build": 0,
  "last_dt_at_build": "...",
  "corpus_built_at": "...",
  "features_built_at": "...",
  "excerpts_built_at": "...",
  "note_written_at": "...",
  "template_versions": {"深季判讀.md": "mtime"}
}
```

**新鮮度檢查**（便宜、不重掃原始檔）：重用快取前，比對該對象目前在 `thread_index.json` 裡的 `message_count`/`last_dt` 有沒有變——變了就只重建那一個對象，不影響其他人。

**範本漂移檢查**：比對快取記錄的範本 mtime 跟目前範本檔案的 mtime——如果範本在筆記寫完之後被改過，不要靜默沿用舊筆記當作最新結果，主動提示「這篇筆記是在你上次改範本之前寫的，要不要重寫」。

**排名步驟不需要快取**：純 JSON 運算、本來就便宜，每次問聚合問題直接現跑即可。

實作見 `程式\共用\cache_index_template.py`。
