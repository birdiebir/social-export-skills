# 查證與跟使用者協作

2026-10-01 新增。內容整理自同一人兩個帳號的匯出專案，連續做過多批補強之後的教訓。這份管的是質化分析到寫結論的階段：結論從哪裡來、數字怎麼查證、使用者的說法跟資料不一致時怎麼處理。資料層的坑（解析、覆蓋檢查、多帳號計數）在 `social-export-analysis` 的 `references\`，這裡不重複。

以下例子的人名、帳號、數字都是虛構的。

## 1. 結論以全讀版為準

- **抽樣寫成的筆記錯誤率非常高**。某專案對一批抽樣時期寫的中量筆記做語意複查，四十多篇裡幾乎每篇都要改，常見問題見 `分層.md`「機械驗證通過≠敘事正確」。所以：
  - 寫進知識庫或報告的結論，來源筆記要先確認是全讀版：meta 有記全讀涵蓋率，而且 coverage 是 PASS。
  - 抽樣版只能當線索。要把它寫成結論，先全讀重寫，或回 L1 逐則查證那一句。
  - meta 裡要清楚標出「讀法」（全讀／抽樣／關鍵字＋局部讀），之後的人才知道哪些可以信。
- 語意複查一定要由第二個 agent 做，不能讓寫筆記的 agent 自己複查。複查時正文引號裡的字也要對回 L1，因為機械驗證只會檢查 quotes.json。
- 範圍很大、使用者還沒決定要不要全讀的對象（例如訊息量最大的一對一對話），可以先只做語錄逐字驗證，再請使用者決定要不要全讀。不要先把抽樣結論寫進知識庫。

## 2. 一手、二手來源

- 下面這些都是二手來源：agent 回報、PM 看板、綜合文件、舊筆記，甚至使用者的口述。進決策紀錄或知識庫的數字、「唯一／從未／全部」這類全稱句，都要回 L0／L1 用腳本重算。
- 數字對不上時，先把兩邊的口徑寫出來，再判斷誰錯。常見的口徑差異有：
  - 日期切點用 `>=` 還是 `>`
  - 有沒有算系統紀錄、範本字句
  - 只算有文字的訊息，還是全部訊息
  - 有沒有算進兩個帳號共有的串
- PM agent 的結論也會錯。真實案例：PM 的切點算進了換帳號當天，數字因此多了約兩成，後來是 PM 自己第二輪回 L0 查證才更正。

## 3. 使用者的說法跟資料不一致時

1. 兩邊都查。用 L1 全量統計，再到 L0 原始檔抽樣，核對 sender 欄位。
2. 照實回報：哪部分成立、哪部分不成立，附上數字和分類。不要因為使用者語氣篤定就改結論，也不要硬駁。
3. 資料判斷不了的部分才問使用者。例如：當時是不是本人在用、帳號有沒有借給別人、有沒有被盜。
4. 使用者補充的事實寫成勘誤條目，再同步修正受影響的筆記。

> 虛構範例：使用者說「換帳號以後，舊帳號都只有收訊息、沒有回」。用發言者別名統計後發現，換帳號後舊帳號自己發的訊息不到同期的 1%，幾乎都集中在某兩年的二手交易和應徵詢問。回報方式：「『主要收訊息』成立，『完全沒回』跟資料不符：某年到某年回去登入過，回了約 N 則，主要是交易。其中某週的社團洗版是不是你本人發的，資料看不出來，需要你確認。」使用者回答「那週帳號借給別人用」，就寫成勘誤，並把該週相關的 PR 審閱和筆記改成「帳號被借用，不是本人言論」。

## 4. 事實題只有使用者知道，要一次問完

- 資料裡查得到的，自己查，不要問。
- 查不到、但會影響結論的事實，整理成**一次問完的編號清單**，不要在不同時間一題一題追問。例如：某張證照到底有沒有考、某個獎是從哪裡得知的、交往日是哪一天。每題附上：
  - 目前資料怎麼說（出處）
  - 為什麼查不出來
  - 建議答案或建議處理方式，讓使用者可以只回「照建議」
- 收到答案以後：
  - 寫進**勘誤檔**（單一來源，每條有編號），由產生器在相關頁面並列顯示。
  - notes 只改錯的句子。舊版存 `_superseded\`，改前、改後和理由寫進 meta 的修正紀錄。
  - 原樣保存的切段文件一個字都不要改，用勘誤並列的方式處理。

## 5. 讀訊息時的判讀陷阱（質化階段）

- **文字欄只有「IP 位址：…」的那則**，是本人傳的讚貼圖、貼圖或相片，不是系統通知。「本人未回覆」常常是這樣誤讀出來的，判讀時看 L1 的 `type`／`media`。
- **時區**：匯出檔的時間是固定一個時區。事件發生在國外時，先換成當地時間再寫日期。「15 號早上告白」在當地可能是 14 號晚上。
- **範本字句、Meta AI 的回答**不是本人說的話，不能當語錄，也不能寫成「本人說」。
- **「斷聯」先查是不是換帳號了**：去另一份匯出看同一個人的對話有沒有接下去。真實專案裡，好幾篇「某年起斷聯」其實都是換帳號。
- **帳號歸屬**：寫「哪個帳號做了什麼」之前，先看資料來自哪一份匯出、發言者別名是哪個。本人的英文暱稱可能剛好跟某個帳號同名，名字不等於帳號。完整規則見 `social-export-analysis` 的 `references\multi-account.md`。
- **代名詞與身分**：寫之前先查 identity 模組的性別欄位，不要從暱稱的語感去猜（見 `踩坑.md` 第 41 點）。

## 6. 讓使用者填清單、再回寫（2026-10-01 新增）

- **使用者的填法常常跟腳本預期的不一樣**。真實案例：清單每一列都有「你的決定」欄，使用者卻在段落標題底下寫了一行「決定：全部都是」，每列的欄位都空著。回寫腳本只讀每列的欄位，dry-run 顯示「人物變更 0 筆、全部略過」；把答案轉成答案檔再帶入，才正確寫入。所以：
  - 回寫腳本**預設 dry-run**，先印出「會改幾筆、各等級前後人數」，確認後才加 `--apply`。
  - **讀到 0 筆是警訊，不是「沒有要改的」**。先回頭看使用者實際怎麼填。
  - 清單開頭寫清楚兩種填法：逐列填，或在對話裡回「題號＋答案」。也可以明講接受「整段全部是」這種寫法，腳本要認得。
  - 使用者在對話裡回的答案，先存成 UTF-8 檔，再用 `--answers-file` 帶入，不要把中文直接放在命令列參數（主控台編碼會把字弄亂）。
  - verify 沒過就拒絕寫入。寫入前把舊檔存到 `_superseded\`，meta 補修正紀錄。腳本收工前搬進專案的 `tool\scripts\`，下次使用者再勾新答案時可以重用。
- **使用者的確認要能覆蓋規則判定，而且雙向都要有**：
  - 「是同一人」→ 確定，即使規則只找到同名證據也一樣。另外記一種證據「使用者確認」，verify 才分得出它跟只有同名的不同。
  - 「不是同一人」→ 獨立的「不同人」等級，頁面顯示「已確認不同人」，不給合併提示。不要把它退回「僅同名」，否則下次規則一跑又會被拉回待確認。
  - 同名但其實是兩個人 → 允許拆成兩列。
  - 已經確認過的答案，預設不覆蓋；有衝突就跳過並列出來。
- **設計清單時把把握度排序**：把握高的放前面，讓使用者可以快速掃過；每題附判斷依據摘要和建議答案，不放私訊原文。共同人物的證據，「兩份匯出裡同一個群組的成員名單都有他」比只有同名強很多（細節見 `social-export-analysis` 的 `references\multi-account.md` §7）。

## 7. 抽樣寫成的大型對象：先做嚴格引文驗證，結論等全讀（2026-10-01 新增）

量體最大的對象（例如十幾萬則的長期一對一對話）常常是抽樣讀寫成的，使用者也可能還沒決定要不要全讀。這時先只做**嚴格（strict）引文驗證**，規則如下：

- 每個「代表性片段」都要對到 L1 的**同一則訊息**：發言者相同、同一分鐘（沒寫時間的片段，算在前一個明示時間的 60 分鐘內），用刪節號切開的每一段要依序是那則訊息的子字串。
- 正文裡其他引號（「」『』）一律登記在 `quotes.json`。正文有引號但沒登記，或登記了但正文已經沒有，都算 FAIL。
- 下面這些都不算通過：改寫、截斷後拼接、跨訊息合併、只差標點或空白，以及把 L1 文字尾端的心情回應（表情＋人名）抄進引文。
- 真實案例：改用 strict 前，引文只過了大約七成。修正以後有兩句結論被推翻，例如一個暱稱其實出自不同的語境，不能拿來當說話風格的證據。

strict 只能證明引文存在、沒被改過，**不能證明抽樣敘事是對的**。全讀之前不要從抽樣版寫新結論進知識庫，已經寫進去的要標「抽樣版，待全讀確認」。

全讀時的讀稿準備：
- 依季切分
- 先把心情回應從訊息文字拆出來
- 標出範本句
- 時間附上當地時間
- 語意複查由第二個 agent 做

## 8. 所有模組都改 strict，正文引號用登記制（2026-10 新增）

- **舊版驗證全過，不代表引文正確**。舊規則只比到同一分鐘，而且比對前先去掉空白，所以全部 PASS。改用共用的 strict 驗證器（範本：`程式\共用\quotes_strict_template.py`）後，一次抓出數百筆不過，原因分布大致是：
  - 同一分鐘但秒數抄錯：佔絕大多數
  - 抄進心情回應尾巴
  - 只差空白
  - 跨訊息、改寫、發言者錯：0 筆
- **做法分兩階段**：
  1. 唯讀盤點，把不過的依原因分類。
  2. 用回寫工具只修可以機械修正的三類（補秒數、截掉心情尾巴、照 L1 抄回空白）。修完再把各模組的預設改成 strict。
- **正文引號另外處理**。結構化語錄之外，筆記正文的「」『』可能有好幾千處。規則：
  - 引號裡的字必須是該篇範圍內 L1 的逐字。
  - 不是引文的術語、名稱、分析用語、系統文字，登記在 meta 的 `inline_terms`。
  - 引的是別的對話串或別的 L1 檔，登記在 `inline_source`，verify 會回出處逐字核對。
  - 沒登記又不是逐字的，verify 印 WARN。
- **不是逐字的引號怎麼處理，有四種**：改回原文、拆成幾段分別引、改成轉述（拿掉引號）、維持（確認其實是逐字）。
  - 第一輪抽樣處理時，抽查發現約一成漏判，所以改成全量處理。
  - 全量處理改了數十處會影響結論的地方，例如話其實是本人說的、發言者誤植、引文漏掉關鍵的半句。
- **跟外文有關的引號**：彎引號和撇號照原文；外文對話引原文，中文意思寫在引號外的括號裡，不要把譯文放進引號冒充原話。

## 9. 新寫的敘事一律做語意複查（2026-10 新增，錯誤率實測）

同一個專案的實測：
- 補讀一個群組後寫的新筆記，抽查約 40 句，錯了將近四分之一。
- 新寫的人生時間軸，87 個事件錯了約三成。

錯誤類型重複出現：
- 推測寫成事實、誇大（「開始做」其實只是「加入社團」）
- 口徑不一致
- 時間錯置、把回報日當成發生日
- 年齡算錯
- 標題暗示了沒有證據的學校年份
- 帳號歸屬寫錯

這些錯，strict 驗證和覆蓋檢查**都抓不到**。所以：

- 任何新寫的敘事（筆記、時間軸事件、年度回顧亮點、知識庫結論），都要派**第二個 agent** 回 L1 看前後文逐句複查。派工時就把複查 agent 排進去。
- 複查 agent 的方法：
  - 每個事件回 L1 看前後各幾則訊息。
  - 系統紀錄逐筆對。
  - 統計數字用另一套程式獨立重算（例如年度統計抽 8 個年份重算，全部吻合才算過）。
  - 居住時段用登入國家逐日核對。
- 複查留下的待查句，要由下一個 agent 回 L1 確認後才改，不要照複查意見直接改。也要記得：有些「待查」的前提可能已經過期，例如另一份筆記早就改過了。

## 10. 修正工具的共同模式（2026-10 新增）

這一輪新做的回寫工具都照同一個模式：strict 語錄修正、正文引號修正、個資遮罩、知識庫回填、跨帳號人物確認回寫。

1. `scan`：產生判定檔。檔案含原文時，只能放在 tmp。
2. 人或 agent 填「判定」欄。
3. `apply` 預設 dry-run，印出會改幾筆。
4. `--write`：先備份到 `_superseded\`，只改允許的區塊（改到其他鍵就拒寫），並補修正紀錄。
5. 自我檢查：處理過的列不能再出現在 WARN；寫出來的 yaml、json 要能讀回。

另外兩條原則：
- **只有唯一候選才自動寫**：同一分鐘有兩則候選、錨點在目標筆記出現不只一處，就整筆或整批不寫，留給人判斷。
- 高敏感的項目，不會被「全部照建議」這類整段答案套用，要在那一列單獨填。

## 11. 長尾全讀批：把錯誤率壓到 5% 以下（2026-10 新增）

同一個專案後來把一百多個小對象（多半幾十到幾百則）全部全讀，分十幾批平行寫，每一到兩批配一個語意複查。上一輪新敘事錯誤率兩到三成，這一輪各批事實錯誤率 1.4%～4.6%，嚴重 0。差別在三件事：

- **校準閘門**：第一批人物、第一批群組寫完，先各派一個複查，錯誤率超過門檻（例如 15%）就停下後面的批次。人物的結果不能直接套到群組，群組要另設一道閘門。
- **共同規則會長大**：每次複查找到的新錯誤類型，馬上補進所有 agent 開頭都要讀的共同規則，並註明是哪一批發現的。最後累積到四十條，下面是最常犯、最通用的幾條：
  - **「A 說 X，B 回 Y」的 Y 一定在 X 之後**。把幾句壓成一串時，本人的回覆常被放到最後，實際上夾在中間。這是最常見的錯，寫完要照 seq 順序再對一次。
  - **數字不寫概數**：連發逐則數，間隔用時間相減（「十幾分鐘」其實是 11 分 59 秒）。單次事件不寫成「會」「常常」。
  - **全稱句、否定句先找反例**：「都是」「每次」「只剩」「不會追問」，以及群組的「多半」「最多」，都要先分項算過，過半才寫，而且附上數字。
  - **「第一句」「最後一則」要對到第一個／最後一個 record**，包括本人的短回覆、貼圖、心情紀錄、打招呼。
  - **代名詞**：資料裡沒有性別依據就不寫他／她。本人用「你／妳」、第三人隨口說的「他」都不算依據。收工前用腳本掃一次引號外的他／她。
  - **不替看不到的內容命名**：相片不要寫成「課程截圖」。對方內容空白時，不要補出「找不到訂單」這種結果。對話只是停了，就寫「之後沒有後續」，不寫「談不攏」。對方的動機（詐騙、拉人頭）要原文寫得出來才寫。
  - **主詞是「我們」「We」的，不能推成本人一個人做的**。本人傳的連結或檔案也不等於本人的作品。
  - **群組在場**：本人在群的期間，用入群和退出事件來界定。入群後才看得到的舊訊息、「對你的訊息傳達了心情」這類系統文字，都不能當成在場的證據。要看得到加入，才能寫「中途離開」。
  - **驗證腳本只查「整串有沒有這幾個字」**：短引文（「好」「Ok」），或同一句話在不同日期都出現時，發言者和日期要自己核對。
- **規則追溯要分開算**：新增的必查項（例如代名詞）如果是某些批次寫完之後才加的，複查時要說明是否追溯計入錯誤率。實例：某批事實錯誤率 1.4%，把代名詞也算進去就變成 44%。這種情況判 PASS，另外派一批補掃，不要整批重做。

**事實彙整查核**（把各批回報的「事實線索」合併、回 L1 查核，做成勾選表給使用者）：
- 同一件事常分散在不同批，要合成一筆，列出全部出處。拆成兩個 agent 做時，每一組跨邊線索都指定一個負責合併的一方（做法見 `social-export-analysis` 的 `references\parallel-agents.md` 長尾段）。
- 判斷「L1 沒有」之前，一律做全文搜尋。查詢工具如果只印每則前 200 字，命中在後段（例如連結預覽）的就會被漏掉。
- 拿別串當佐證時，先看那一則是在回答什麼問題。例如前一則問的是另一場考試。
- 「科目清單」「候選清單」不等於「選了這個」。佐證要回 L1 看全文，回報只引其中一項時特別容易出錯。
- 回報裡「事實線索」那一行，常常寫得比筆記本文還肯定。複查批如果規定不查事實線索，這一行就要由事實查核另外抓。

**對方整串內容看不到**：先用唯讀腳本看一次原始 HTML 的結構，只印標籤和字數，不印內容。原始檔也是空的，就是匯出本身缺漏。這時照寫「看不到」，不推測，也不要把沒有發言者的紀錄歸給任何人（細節見 `social-export-analysis` 的 `references\pitfalls.md` §E2）。

## 12. 結案寫入：把勾選表、回填表寫進知識庫，再做一次獨立查核（2026-10 新增）

專案收尾時，把使用者勾過（或「空白＝照建議」）的事實寫進事實表、時間軸和知識庫，再派一個 agent 回 L1 獨立查核。實測母體八十多筆，錯 3 筆、措辭要改 8 筆。錯的幾乎都出在**這一輪新寫的句子**，已經查核過、只是搬位置的那批錯 0。會讓結論寫錯的有這幾類：

- **從勾選表、查核紀錄抄日期，要再換一次當地時間**。這些中間表常寫匯出檔的時區（例如台灣時間），本人或家人當時在國外時差一天。前一輪已經講過要換，回填 agent 照抄中間表還是會漏。
- **「看得到的最早時間點」不等於事件發生日**。例：私訊裡看得到「對方說已經收到通知」的日期，不能寫成寄出日；L1 沒寫的細節就不要補。寫成「之後寄出（哪一天私訊沒寫）」。
- **只有一次紀錄，不寫成規則或習慣**。「新管理員要大家同意」只出現過一次；「常推掉」實際只有兩次。寫成「這一次」「推掉過兩次」，或附「只有這一次的紀錄」。
- **角色與動作要有系統事件或原話**：「組長」「被加入群組」「賣出」這類詞，L1 沒有人這樣稱呼、沒有入群事件、沒有成交，就是推測。改寫成「負責統整的一位組員」「起在群組裡（入群紀錄看不到）」「出售、最後沒成交」。
- **查核分配**：新寫入逐筆查；前一輪已核、這輪只是換位置的，抽查兩成左右就夠。
- **個資值的核對**（帳號、證號）用程式只回傳「一致／不一致」，不要把值印進回報或查核紀錄。

勾選表的「你的決定」空白要先講好代表什麼（例如「照建議」），並寫在表頭；寫入 agent 依每列的「去處」分工，收工時各自把全表再掃一遍，確認每一列都有人接。
