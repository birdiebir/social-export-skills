# 與 `social-export-analysis` 的依賴關係

## 偵測邏輯

在跑任何模組之前，先檢查目標專案是否已經有結構化資料：

```
<project>/analysis/output/messages/data/thread_index.json
<project>/analysis/output/social/data/friends.jsonl
```

- **兩者都存在且非空**：跳過本節，直接進對應模組的 pipeline。
- **不存在，但 `<project>/raw/` 有原始匯出**：先觸發 `social-export-analysis` skill，但明確限定範圍。
- **兩者都不存在、也沒有 `raw/`**：請使用者提供原始匯出（zip 或已解壓的資料夾）。

## 限定範圍：只需要三個 domain

`social-export-analysis` 的通用萃取涵蓋很多 domain（`ads_information`、`marketplace`、`security_and_login_information`…），但本 skill 目前的三個範例模組（關係、群組、風險）只依賴：

| domain | 提供什麼 | 誰用 |
|---|---|---|
| `identity` | 本人姓名別名解析 | 全部模組的 `SELF_NAMES` |
| `social` | `friends.jsonl`（好友清單，含 `friend_since`） | 關係模組的 `friend_since` 比對 |
| `messages` | `thread_index.json`（每個對話串的量化摘要）＋`derived/messages_by_person\|group/` 的完整聊天記錄 | 關係／群組模組的候選排名與語料來源 |

風險模組額外需要 `posts`/`comments`/`group_activity`（`pr_risk` 相關 domain 的抽取結果），若使用者只問關係/群組問題，不需要觸發這幾個 domain 的抽取。

**觸發 `social-export-analysis` 時，明確告訴它只需要跑上述必要的 domain**，不要要求它跑完整套（marketplace/ads/security/photo_library 這些跟本 skill 三個範例模組都無關，屬於浪費）。

## 為什麼要限定範圍

「輸入是原始匯出整包」這個決策本身會一直誘使本 skill 為了「自成一體」而慢慢長出自己的萃取邏輯，最終變成把 `social-export-analysis` 的活重做一遍。這條邊界規則要當硬規則執行，不是備註——萃取/解析邏輯的唯一負責方是 `social-export-analysis`，本 skill 的模組永遠只消費它的產出（`paths.py`／`fb_common.py`／`name_match.py`／`hardlink.py` 直接 import，不複製邏輯）。
