# 三層分析深度（輕／中／深）

跨模組通用的分析投入分級，取代早期只在 `relationships/` 出現、且綁死「排名前 N 名」的深/輕兩層規則。**分層現在是依需求指定的，不是排名自動決定的**——預設情況下，任何目標（對話／群組）只需要有 L1 原始資料（見下方「預設狀態」），不必也不應該自動跑到任何一層分析；使用者針對特定目標明確要求某一層時才做。

這條規則是從一次真實專案（本文件寫成當下，把 `relationships/` 數十位聯絡人全部做到中層、約 10 個群組全部做到中層＋100% 全量通讀）反推整理出來的，取代舊版「深層=排名前10，輕層=排名11-30」的寫法。

## 預設狀態：只要 L1，不要分析

新建或擴充一個模組時，第一步永遠是先確保 L1 抽取產出齊全、可瀏覽（見 `social-export-analysis` skill；本 skill 消費其產出）——例如 `messages/report.html` 這種依訊息量/篇數排序、可搜尋篩選的存檔列表，讓使用者能自己看到「有哪些目標、量體多大」。**不要因為做完 L1 就順手往下推進到 L2 候選排名或任何質性判讀**——使用者可能只是想先看看資料有什麼，分析與否、做到哪一層是另一個決定，除非使用者明確說要分析，否則停在 L1。

## 三層定義

| 層級 | 對應 | 產出 | 適用情境 |
|---|---|---|---|
| **輕 (light)** | L4 量化特徵，通常不做 L5 | 基本統計（訊息量、時間跨度、密度）＋規則式標籤或極短的一段自動摘要；SnowNLP/jieba 之類便宜的 NLP 附加分析 | 目標數量多、單一目標判讀價值低、或使用者只想要「大致看一下」 |
| **中 (medium)** | 既有或新做的 L5 質性敘事 ＋ **結構化事件/語錄/語氣萃取** | `note.md`（沿用既有敘事或新寫一份）＋ `timeline.json`（事件時間軸）＋ `quotes.json`（精選逐字語錄）＋ `sentiment.json`（固定量表的語氣序列，用於畫折線圖）；語錄與涵蓋率必須通過機械化驗證（見下方「驗證是中層以上的硬性門檻」） | 使用者想要「看得出這段關係/這個群組實際發生過什麼」，但還不到量化建模的投資報酬率 |
| **深 (deep)** | 中層全部 ＋ 完整量化建模套件 | 中層的所有產出 ＋ 迴歸趨勢／PCA＋KMeans 關係階段分群／TF-IDF 主題詞這類完整統計建模，通常搭配月粒度特徵矩陣 | 少數手選的旗艦目標（單一好友原型模組 `ai_<friend>/` 是原型），值得深入才做，不要對大量目標複製這套全量統計 |

**深層＝中層的超集，不是平行的另一套做法**——深層目標一樣要有 `timeline.json`／`quotes.json`／`sentiment.json`，只是額外疊加量化建模。舊版「深季判讀」範本（逐季細讀）仍然是深/中層質性敘事的輸入來源之一，但中層本身的核心產出是「事件/語錄/語氣」這三份結構化檔案，不是「讀得多細」。

**挑深層候選時，排名複合分數只能決定候選順序，不能直接決定「值得深挖」——尤其當分數是用「百分位排名」加權而非原始數值時**（2026-09-17 稽核新增，見 `分析\踩坑.md` 第 26 點）：把某真實專案的排名公式回歸還原後發現，它是先把每個特徵（訊息量/跨度/近期性/密度/媒體豐富度）轉成「贏過候選池裡幾 % 對象」的百分位，才加權加總。這種做法對「量級」不敏感——候選池裡有大量極低量體的雜訊候選（陌生人/交易對話）時，一段僅十來天、不到一百則訊息的短期交易只要贏過池子裡大多數雜訊候選，就能拿到接近深層門檻的高分，擠進深層量化建模候選，量化結果卻自己承認「樣本跨度太短、看不出顯著趨勢」；反過來，一段訊息量上萬則級但已停止聯絡多年的真實長期關係，可能因為「近期活躍度」被拖累，總分被壓到候選池前段之外，完全排不進中層以上分析。**排名分數前 N 名，只代表「這些是候選」，不是「這些都值得做深層」，尤其分數本身可能對量級不敏感。**挑深層候選的最後一步，一定要加一道質性初篩：另外看一眼候選的原始數值（訊息量/時間跨度，不是轉換後的百分位），自問「這個對象有沒有值得深挖的敘事理由」（例如關係跨度夠長、事件夠戲劇化、內容夠豐富到量化建模不會做在近乎空的樣本上），不是分數排前面就自動派工深層，也不要假設分數高就等於量體大。

**中層的事件/語錄擷取數量，要依內容量體級距調整，不能用固定張數**（同上次稽核新增，見 `分析\踩坑.md` 第 27 點）：曾經發生同一套中層 pipeline 對上萬則訊息的目標和兩三千則訊息的目標，都擷取出幾乎一樣多（約 N 則，固定值）的 `events_narrative` 事件——高量體目標的真實壓縮比因此是低量體目標的好幾倍，等於漏掉大量原本值得記錄的內容。擷取數量的上限該隨來源量體分級距（例如每 N 則訊息 ≈ 1 則候選事件），而不是不管量體大小都抓同一個張數。

## 整包結構與選單（依目標＋分層，完整輸出樹）

`分析\擴充.md` 明講「刻意不做自動生成模組骨架的工具」——那條規則管的是「寫一支程式碼幫你生出一整個新模組的腳手架」，跟這裡要記的東西不是同一件事。這裡要記的是：**給定一個目標＋一個分層選擇，最終會落地哪些檔案**，讓使用者事前看得懂「選中層會拿到什麼」，也讓 agent 有一份清單可以核對「這次交付是不是齊了」，而不是每次臨時回想。落地方式還是照舊：agent 依下面的選單，手動走對應模組 `說明.md` 的 pipeline 步驟去產生這些檔案，不是跑一支生成器。

**任何分層都以 `social-export-analysis` 建好的 L1 原始資料區為底（不分層，永遠都在）**，例如 `messages/report.html` 這種依量體排序、可搜尋的存檔列表。以下是關係／群組兩個範例模組，在各分層下實際會有的檔案：

```
analysis/output/
├── messages/report.html                     # L1 原始資料區，跟分層無關
├── relationships/
│   ├── data/thread_ranking.jsonl, top30.json # L2 候選排名，跟分層無關（批次跑一次）
│   ├── quant/<slug>/
│   │   ├── messages_full.jsonl                # 輕以上都有
│   │   ├── feature_matrix.csv                 # 輕/中＝年粒度；深＝月粒度＋迴歸/PCA+KMeans/TF-IDF
│   │   └── report.html                        # 輕以上都有
│   └── notes/<slug>/
│       ├── excerpts/*.md                      # 質性判讀前的摘錄素材（中/深層的敘事基礎）
│       ├── note.md                             # 中以上都有（質性敘事本體）
│       ├── timeline.json / quotes.json / sentiment.json   # 中以上都有，quotes 必須過 verify_quotes_template.py
│       └── profile.md                          # 選配：人物側寫二次彙整，不分層
└── group_analysis/
    ├── data/group_ranking.jsonl, top10.json    # L2 候選排名，跟分層無關
    └── quant/<slug>/
        ├── messages_full.jsonl                 # 輕以上都有（含系統事件標記）
        ├── member_summary.json                 # 輕以上都有（規則式標籤）
        ├── report.html                         # 輕以上都有
        └── coverage.json / events_narrative.json / quotes.json   # 中以上才有，全量通讀＋須過兩支驗證腳本
```

選單（表格版，方便對照「選這層＝多這些檔案」）：

| 目標類型 | 輕 | 中（＝輕 ＋） | 深（＝中 ＋） |
|---|---|---|---|
| 聯絡人（`relationships/`） | `messages_full.jsonl`、年粒度 `feature_matrix.csv`、`report.html` | `note.md`、`timeline.json`、`quotes.json`、`sentiment.json`（過驗證） | 月粒度 `feature_matrix.csv`、迴歸趨勢／PCA+KMeans 分群／逐季 TF-IDF 主題詞、深季判讀補強 `note.md` |
| 群組（`group_analysis/`） | `messages_full.jsonl`、`member_summary.json`、`report.html` | `coverage.json`、`events_narrative.json`、`quotes.json`（全量通讀＋過驗證） | 月粒度 `feature_matrix.csv`（把聯絡人深層的「兩人 self/other」特徵改寫成群組整體的發言集中度 `top_sender_share`／`gini_concentration`／相異主動發起人數 `distinct_initiators`）、`regression_results.csv`（線性迴歸，見下方「群組深層」小節的統計檢定力提醒）、`phase_clusters.csv`（PCA+KMeans 群組生命週期分群）、`flagged_months.json`、`topic_keywords_by_quarter.json`（jieba+停用詞逐季關鍵詞，詞庫依群組性質置換，如版務向/揪團向/粗口向）、`field_notes.md`（欄位定義與取捨記錄） |

**怎麼用這份選單**：使用者對某個目標指定分層時（例如「幫我對 X 做中量分析包」），先對照這張表列出「這次會多出哪些檔案」讓使用者確認範圍，交付後也拿這張表逐項核對有沒有漏做——尤其中層以上漏做驗證是最容易被忽略的一項。目標類型不在表上（新模組）時，先走 `分析\擴充.md` 定義好模組形狀，再回來把新的一列補進這張表。

**判斷一篇既有筆記做到哪一層，不要相信它 frontmatter 裡的 `tier` 欄位字面值，要看它實際有哪些檔案**（2026-09-17 稽核新增，見 `分析\踩坑.md` 第 30 點）：分層定義本身會隨時間演進（例如這份文件取代的舊版「深層=排名前10，輕層=排名11-30」兩層制），舊制底下寫的 `tier: light` 在當時可能代表「有完整 L5 敘事、只是沒有量化建模」，換算成現行三層制其實等於「中」，但既有筆記的 frontmatter 不會在分層定義變動時自動更新。判斷方式：直接看資料夾底下有沒有 `note.md`／`timeline.json`／`quotes.json`（中層特徵）、有沒有月粒度 `feature_matrix.csv`／迴歸/PCA 產出（深層特徵），不要只讀 frontmatter 那一行字。

## 驗證是中層以上的硬性門檻

中層與深層都涉及「聲稱讀過原始訊息、萃取出真實事件與語錄」，這是全架構裡最容易被 LLM 悄悄偷工的地方（意譯、截斷、拼接兩則訊息成一則、自稱「涵蓋率已足夠」但其實沒讀完）。兩支共用驗證腳本收在 `程式\共用\`：

- **`verify_coverage_template.py`**：核對某目標的 `coverage.json` 裡 `messages_read` 是否真的等於來源 `.jsonl` 的實際行數。用於「聲稱全量通讀」的中/深層群組分析。2026-10-01 起優先核對「實際讀取清單」：每批在 `coverage.json` 記下 `seq_range`（或頂層 `read_seqs`），腳本會抓出漏讀、重讀、對錯檔；只有數字時只能給 WARN，因為「重讀 A 段、漏讀 B 段但總數相等」比數字抓不到。
- **`verify_quotes_template.py`**：核對 `quotes.json`（或 `events_narrative.json` 裡的 `evidence_quote`）每一筆的逐字內容，是否能在來源 `.jsonl`（`--jsonl`）或摘錄檔（`--excerpts-dir`）裡找到完全相符的子字串。任何一筆不是逐字比對通過，整份視為不合格，要求重寫該筆而不是整份重跑。

任何中層以上的任務，交付前一律先跑這兩支腳本（依資料來源二選一或都跑），驗證腳本回報非 0 exit code 就是沒做完，不能跳過或用人工抽查代替。完整踩坑細節見 `分析\踩坑.md` 的「語錄/涵蓋率驗證」相關條目。

## 機械驗證通過≠敘事正確：中層以上還要做一次語意層複查（2026-09-22 新增，重大發現）

`verify_quotes`／`verify_coverage` 只檢查「引言逐字存在」與「涵蓋率數字對得上」，**完全不檢查敘事本身有沒有超出證據支撐**。Account A 專案一次性對約 50 篇早期完成、frontmatter 全部標示已過機械驗證的中/深層筆記做語意層複查（不是抽查，是每篇都完整回頭核對一手訊息），結果 **全部判定需要改寫**（約三成 severe、其餘 moderate），且問題模式高度一致，不是隨機誤差：

- **把被拒絕/未實現的提案寫成做過的事**（最常見，至少8篇）
- **單向行為寫成雙向熱絡**（幾乎每篇都有，方向一致地把「本人主動」寫成「雙方」）
- **時間軸密度系統性誇大**，方向一致把冷清期寫成高峰期
- **漏掉全篇最關鍵的收尾轉折**，改用無據推測句代替
- **少數案例憑空捏造字眼／引言**（例如「打工」「補習」「傳說對決」等詞在原始訊息全文搜尋是 0 次；「我110 10」這類正文引言完全不存在——因為只有 `quotes.json` 過機械驗證，note.md 正文用引號寫的話完全是驗證盲區）

**根因**：這類錯誤全部發生在「把逐字語錄／量化統計組織成一篇連貫敘事」這個步驟，是 LLM 為了敘事完整性/可讀性，在缺乏強制核對機制的情況下系統性補完、簡化、誇大細節，方向永遠是讓關係「看起來更長、更密、更熱絡、更完整」，而不是隨機方向的錯誤。

**新增規則**：中層以上交付前，除了兩支機械驗證腳本，**額外要求一次獨立的語意層複查**——不能由原本寫這篇筆記的同一個 agent 自己複查（同一個 agent 傾向認同自己已經做對），要用新的一輪、專門核對「敘事主張 vs 一手資料」的審核（逐一核對時間順序、密度定性用詞、因果推論、正文引號內文字，不只查 quotes.json），且要涵蓋正文的引號內文字（機械驗證的盲區）。這一步的判斷力要求高，實測用 Opus 做複查、Sonnet 做同一份筆記的複查相比，Opus 找到的問題數量與深度明顯更多（Sonnet 找到 5 條，Opus 找到 10+ 條，包含 Sonnet 完全沒發現的「全篇最關鍵收尾轉折被遺漏」與「系統性單向/雙向錯置」兩類問題）——這類語意複查建議用判斷力較強的模型執行，機械驗證與後續照著清單修正則可以用一般模型。（中/深層群組適用，訊息量大時）

群組的中層（甚至輕層想做點像樣的東西時）常常要處理數萬則訊息，不能一次塞給單一 agent 讀完，也不能像早期做法只抽樣 0.5% 就假裝完整。標準程序：

1. 用 `wc -l` 或等效方式確認來源 `.jsonl` 總行數，記錄為 `total_messages`。
2. 依日期切成好幾個子區間（每個子區間目標訊息量抓 2-5 萬則以內，依實際情況調整），分派給多個獨立 subagent，每個 agent 只負責一個子區間，依月切批（每批約 500-1500 則）逐批完整閱讀，輸出該子區間的中繼檔（`chunk_A.json` 這類，含批次清單＋候選事件＋候選語錄）。
3. 全部子區間讀完後，另一個 agent（或同一個 controller）合併所有中繼檔：事件與語錄依時間排序合併，跨全期通盤去蕪存菁（不是每個子區間各自硬湊數量），保留跨時期的敘事弧線變化。
4. 合併結果寫出 `coverage.json`／`events_narrative.json`／`quotes.json`，跑上一節的兩支驗證腳本，通過後刪除中繼檔。

這套程序在小群組（數千則以內）可以省略拆批，單一 agent 一次讀完即可。

## 一致性做法：先做一份範例，審核過，再讓後續批次照抄

有多個同類目標（例如 30 位聯絡人、10 個群組）要做到同一層時，先挑一個當「設計基準」目標，完整做完＋人工／reviewer 審核過，把審核通過的**實際輸出檔案**（不是另外寫一份文字範本說明）當作後續批次的參照——直接告訴後續 agent「照這份已審核通過的檔案的區塊順序/CSS class/資料格式做，這份比任何文字描述都準」。純文字範本容易在細節上被不同 agent 各自詮釋走樣，一份具體、已驗證的範例檔案不會。

## 群組深層（2026-09-18 補上具體設計，取代原本「尚未定義」）

聯絡人深層的核心是「兩人 self/other 互動特徵」，群組沒有單一「對方」，改寫原則：

- **發言集中度取代兩人親密度**：`top_sender_share`（最高發言者佔比）、`gini_concentration`（發言分布不均度）、`distinct_initiators`（相異主動發起人數）——這組特徵解釋群組「怎麼萎縮」比單純的訊息量趨勢更有解釋力（例如可能是「收斂成少數人偶爾發言」，也可能是「邊緣成員退出但核心話語權佔比不變」，兩種機制看起來都是「活躍度下滑」但成因完全不同，量化時要把這兩種情況分開解讀，不要看到集中度變化就直接下結論）。
- **關鍵詞詞庫依群組性質置換**：聯絡人深層原本用戀人向的相戀/未來規劃詞庫，群組要換成貼合實際內容的詞庫（版務管理群→封鎖/警告/禁言；朋友揪團群→揪團/開黑/語音/聚會；閒聊互虧群→粗口/嗆人詞），從既有中層 `group_note.md` 的質性側寫裡挑高頻詞，不要照搬聯絡人模組的詞庫。
- **時間跨度差異大時，`month_idx` 的定義要留意**：訊息量大的群組如果時間跨度長（例如 8 年以上）且常有連續數月至近一年的長期沉寂，用「有訊息月份的序號」當 `month_idx` 會把長期沉寂壓縮成單一步階，扭曲迴歸斜率的時間意義；改用「相對於首個有訊息月份的實際日曆月數」，並額外加一項「距上次有訊息月份的沉寂月數」特徵，能更準確捕捉「長期沉寂後偶爾復甦」這種生命週期樣態。時間跨度較短（3-4年內）、零訊息月多為單月散布時，用序號式 `month_idx` 問題較輕微，兩種做法都可以。
- **統計檢定力高度取決於活動型態是否單調，不是訊息量大就一定顯著**：漸進式衰退型的群組，迴歸容易拿到大量顯著特徵；「高原＋斷崖」式驟降型（活躍度長期持平、某個月突然崩落）的群組，線性迴歸天生檢定力不足，容易大部分特徵都不顯著——**這不代表分析做壞了，要如實呈現並解釋型態原因**。PCA+KMeans生命週期分群在兩種型態下都相對穩健，即使迴歸大多不顯著，分群仍可能抓到迴歸看不到的階段轉折點，值得兩種方法都做、互相補強解讀，不要只做迴歸。

## 涵蓋率追蹤（2026-09-18 新增）

候選池式模組（`relationships/`、`group_analysis/`、`group_posts/` 這類「先排名再挑一批做」的模組）做到一定規模後，需要一個持續追蹤「做了多少、還剩多少、做到多深」的機制，而不是每次要回答這個問題都重新手動數資料夾。

**核心洞察：候選數量佔比會嚴重低估真實覆蓋度，一定要同時算訊息量加權版本**——例如候選池上千個候選只做了幾十個（數量佔比不到 3%），但這幾十個候選涵蓋了全候選池八成以上的訊息量（因為分層方法論本來就是優先做重要/活躍的候選）。只呈現數量佔比會讓人誤以為進度嚴重落後，看不出「其實最活躍的都已經涵蓋了」這個更有意義的事實。

追蹤機制建議做成：
- 一支**可重複執行**的產生腳本（不要手動維護靜態表格，之後每次有新分析完成，重跑腳本就自動反映最新磁碟狀態），對每個候選池式模組計算：候選池大小、已分析數／佔比、**已分析候選的訊息量加總／候選池全部訊息量加總**（這個才是給人看的關鍵指標）、輕/中/深分層分布、依重要性排序的「下一步建議候選」清單。
- 判斷「已分析」時，一律反查已完成資料夾內部的中繼資料欄位（例如 `meta.json` 裡的 `thread_id`／`coverage.json` 裡的 `target`）回頭比對候選池，而不是自己重新對候選名稱做檔案系統安全字元替換去猜資料夾名稱——群組/社團名稱常有特殊字元、emoji、甚至原始匯出檔本身編碼錯亂的情況，猜資料夾名稱容易誤判或漏算。
- 判斷分層時，優先讀該候選 `meta.json` 裡明確寫的 `tier` 欄位；沒有這個欄位的模組才 fallback 用檔案存在與否（有沒有 `regression_results.csv` 等深層檔案）推斷，兩種判斷路徑要在輸出裡註明依據，不要混著用卻不說明。
- 沒有候選池概念的一次性全量模組（例如好友清單、個人動態這類「處理對象只有一份」的模組），不要硬套候選池百分比公式，直接標記「全量／100%」或視情況標記「尚未開始」，並說明原因。
- 輸出機器可讀（JSON，給 AI agent 讀取判斷下一步）＋人類可讀（HTML 儀表板，沿用模組既有的共用樣式）兩份，可參考的通用骨架見 `程式\共用\coverage_dashboard_template.py`。

## 已知落差（尚未回填進正式範本，先記錄）

- 部分聯絡人只有整篇敘事、沒有逐季小節（`note.html` 沒有 per-quarter `<h2>`）時，中層的 `timeline.json` 錨點沒有對應的季度標題可以連——目前做法是在敘事區塊頂端插入不可見的 `<span id="q-<quarter>">` 佔位錨點，讓連結至少能跳到「唯一存在的那段敘事」，而不是死連結。這是資料本身粒度不足造成的降級處理，不是偷工。
- 同理，部分目標沒有既有的量化報告頁（`quant/<slug>/report.html` 不存在）時，中層合併頁的「量化圖表」區塊應該整段省略，改用 `meta.json` 現有欄位（總訊息數、時間跨度）做一個簡單統計區塊頂替，不要為了湊版面去偽造圖表數據。

## 抽樣筆記不能當結論來源（2026-10-01 新增）

上面「機械驗證通過≠敘事正確」那一節講的是全讀筆記也會出錯。抽樣寫成的筆記更嚴重：另一個專案的抽樣期中量筆記，語意複查時四十多篇裡幾乎每篇都要修。所以：

- meta 一定要寫「讀法」（全讀／抽樣／關鍵字＋局部讀）和全讀涵蓋率。分層欄位寫「中」，不代表是全讀。
- 抽樣筆記的結論要寫進知識庫或報告，先全讀重寫，或逐句回 L1 查證。
- 量體太大、使用者還沒決定要不要全讀的對象，先只做語錄逐字驗證（`quotes.json`＋`verify_quotes`），全讀等使用者決定。

細節見 `分析\查證與協作.md`。
