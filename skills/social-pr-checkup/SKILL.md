# social-pr-checkup：社群 PR 健檢與清理

使用者的原則（2026-10-16 定調，每次都照這個）：
- **只刪有 PR 風險的，不是刪掉所有發過的東西**。PR 風險＝政治與敏感言論為主（政治謾罵、嘲諷貶低他人或群體、髒話人身攻擊、歧視、性暗示、公開他人個資、可能違法），加上未來雇主、同事、客戶看到會扣分的內容。
- **動作前一定先派獨立 agent 查核**，查完有疑義的做成勾選頁給使用者決定；使用者沒核准的一則都不刪。
- **品質與風險管理優先於速度**：慢速、不開多分頁平行，觸發平台限制就停。
- **刪掉的東西一律留原文**，做成只給本人看的回顧報告（引以為鑑），只放本機、不上雲。

個人設定（帳號、路徑、埠號、上次結果）在 `references/本機設定.md`（不在 repo 內；複製 `references/本機設定.example.md` 改名成 `本機設定.md` 再填）；這份 SKILL.md 只寫通用做法。

## 什麼時候用、做多大

| 情境 | 範圍 | 大概成本 |
|---|---|---|
| **年度健檢**（每年一次，自己排提醒） | 只看「上次健檢之後」新增的發文與留言＋上次留下的待辦 | 讀幾十～幾百則，半小時～2 小時 |
| **第一次清理**（新平台、新帳號） | 帳號全部歷史 | 讀幾千則、刪上千則，3～4 天（大部分是慢速刪除的等待） |
| 臨時（求職、升遷前） | 公開可見的內容＋搜尋自己名字 | 1～2 小時 |

## 流程

### 0. 開工
1. 讀 `references/本機設定.md`、你自己的 PR 健檢筆記（上次結果與還開著的待辦），以及要處理的平台的處理狀態筆記。
2. 請使用者到平台下載最新的帳號匯出（Meta「下載你的資訊」選 JSON、全部時間；Google Takeout 也重新下載）。匯出放 `<your-path>/<platform>/raw/<date>_<account>/`，唯讀。
3. 長時間工作先設 `/wake`（跨夜要算到隔天早上收尾時間），並確認記憶體夠（Claude Code 在系統記憶體不足時會停掉背景程式）。
4. 年度健檢另做一步：Google 搜尋自己的中英文名字與常用帳號名，看前兩頁有沒有舊言論被轉載（刪了原文也擋不住別人轉貼）。

### 1. 讀：逐則全讀，回報涵蓋率
- 母體＝本人有文字的發文、留言、社團貼文、社團留言、評論、相片說明。純按讚、Messenger 私訊預設不在範圍（使用者決定過 Messenger 不處理）。
- **不能用關鍵字抽樣代替全讀**（一次抽樣漏掉約 3%，補讀數千則才找全）。量大就分批派 agent，每批寫檢查點，最後回報「讀了 N／N（100%）」。
- 年度健檢：只讀上次健檢日之後的新內容，舊的已處理過。

### 2. 判：分級＋理由
- 每則判 高／中／低／無，附一句理由與類別（政治、衝突互罵、歧視冒犯、性、個資、職場、違法灰色、灰色地帶）。
- 判準：沒有辱罵字眼、沒有針對個人的純政治評論 → 不需處理；對群體的辱罵字眼 → 低；對具名個人的辱罵、詛咒、公開他人個資、影射可辨識的人犯罪 → 高／中。本人是受害方或只有詢問沒執行的，如實判低或無。
- 帳號被盜用期間別人發的內容另外處理（照日期整段清，不逐則判斷），但要使用者親口確認那段期間不是本人。

### 3. 查：獨立 agent 查核（一定要做）
- 把要刪的項目抽成輸入檔（原文、上下文、先前理由），派**獨立的 Opus agent**（不是判斷的那個）逐則讀完，判「有 PR 風險／疑似無／不確定」。一個 agent 約 300 則。
- 只有「有 PR 風險」的才進刪除清單（檔名統一用 `audited_*.json`，監看程式只認這種清單）。
- 「疑似無」「不確定」「只涉及本人個資（生日、email）」「合法但有門牌」做成勾選頁，分組列出原文＋查核意見，讓使用者勾，頁面按鈕產生編號字串貼回。

### 4. 使用者核准
- 每批先給審閱頁（原文、分級、理由），使用者說可以才刪。
- 問題一次列成編號清單問完，不要連續跳互動式提問；要長時間等的事記在你自己的待辦清單。

### 5. 刪：本機代操作，慢速
- **不用 Claude in Chrome**（經雲端轉送、共用帳號有隔離疑慮）。用本機 Chrome 獨立 profile＋除錯埠只綁 127.0.0.1，Python Playwright `connect_over_cdp`；每個帳號一個 profile、一個埠，不要混。
- **比對規則只能更嚴不能更鬆**：
  - 一般留言：活動紀錄那一列的時間＝匯出時間（到分鐘）＋原文前 32 字。
  - 社團貼文：社團名稱＋同一分鐘＋原文開頭，且整月只有一列符合。
  - 社團留言：社團頁常找不到 → 到活動紀錄「社團貼文和留言」分類，同一分鐘＋留言內容完全相同＋整月唯一一列。
  - 比不到就跳過，不猜；同時有兩列符合也不刪。
  - 只看「原文開頭」很危險：原文以對方名字開頭時，會配到同一串的別則（早期版本因此誤刪 2 則）。
- 節奏：每則間隔 5～10 秒隨機、每 15 則休息 60 秒、不開多分頁；頁面出現限制、驗證、登入畫面就停。
- 長時間刪除開**獨立 cmd 視窗**跑（不會被 Claude Code 記憶體回收停掉），每條隊伍各寫一個 log；兩支程式不能同時操作同一個瀏覽器。
- 同時開監看：逐筆比對刪掉的那一列跟典藏原文（典藏遮過的電話、地址會誤報，要人工判讀）、通報不在 `audited_*.json` 的刪除。log 每列至少存 240 字。
- 舊貼文的選單可能只有「移到垃圾桶」（30 天後永久刪除），視同刪除。粉專評論不在活動紀錄，要到粉專的評論頁處理。

### 6. 收尾
1. 重試跳過的項目：只重試還沒整月翻過的；整月翻過都沒有的記「找不到（推定已不在）」，並做成可抽查清單。
2. 程式真的刪不到的做成手動檢查清單（附連結、結果下拉、回報字串）。
3. 重產回顧報告與典藏（每則標刪除日期或找不到），清理進度全部記帳（已刪除／找不到／不處理／延後）。
4. 結案統計從 log 算，不手數。
5. 筆記：更新 PR 處理狀態與年度健檢紀錄，派獨立 agent 查核數字與決定後才存檔。
6. 照實寫出過的錯（誤刪、無法確認的項目），不要寫成「全部完成、沒有刪錯」。

## 刪不到的，要跟使用者講清楚
- 別人的截圖、轉貼、引用；刪除後平台端完全清除可能要一段時間（Facebook 刪帳號官方寫最多 90 天）；對方手上的私訊；按讚與被標註（另外在設定改可見範圍）。
- 「找不到」是推定不是確認；粉專關掉評論後的評論公開看不到但無法確認已刪。
